# 全局规则，强制中文

1. 你所有输出、文档、注释、代码备注、解释、总结、方案、日志全部使用简体中文。
2. 编写代码时：代码注释、文档注释、README、API文档、变更记录、备注全部中文。
3. 当生成文档、开发文档、接口文档、设计文档、技术备忘录时，使用中文编写，排版清晰，使用Markdown。
4. 保留代码本身关键字为英文，仅注释和文档中文。
5. 回答用户提问，一律中文，不要切换英文。
6. 执行任务前先理解用户中文需求，输出中文结论。
7. 中文行文规范：避免使用括号补充内容，需要补充说明时另起短句或改写；标题中禁止使用破折号或括号补充，标题保持简洁名词短语。核心文档先给三行以内摘要再展开细节；术语须有定义、有例子、有落地锚点，项目术语登记于项目根 GLOSSARY.md，判据见方法论规范「表述与术语」节。
8. 改动前先查明实际状态，不得以推断代替核实。涉及删除、重构、合并的，先核验该处置的前提是否成立；涉及差异适配的，先逐条查明差异面再动手；涉及划定改动范围的，先穷尽该范围内的同类实例总数。具体形态：删一个字段先核其写入方与读取方；拆一个文件先核其运行环境是否允许多文件；合并两处重复实现先逐字比对语义；跨版本适配先查明变更记录与实际出入；划定改动范围先数清范围内同类实例的总数，不得只看已见到的那一个。

# 子Agent委派规则

根会话是调度者，保留用户意图、约束、路由、仲裁、裁决与最终验收权，不直接承担实现类工作。

## 何时委派

派发前先判任务性质。第一问是这个任务是只读的吗。目的只是获取信息、无专属产出物的探查型只读任务，派 scout，不再查表。产出接口评审报告、巡检报告或审计报告等专属产物的职责型只读任务，按产出物查「角色与交接」节的派发表，派对应只读代理。非只读任务同样查表。承接者收到不符合自身职责的任务时停止并报告派发类型不匹配。

**只读的探查、调研、方案比选、环境勘察、资料检索，一律派 scout。** scout 由 pi-subagents 随带，随 subagent 工具即可用，无需安装本仓库代理定义，也无需前置输入，形态为：

```
subagent({ agent: "scout", task: "<要查清的问题>", cwd: "<项目根>" })
```

**禁止与改派。** 只读任务不得派给任何具备写权限的 ddd-* 代理，即使任务看上去很小。承接者的拒绝导致该次子任务验收判 rejected，属预期信号而非代理异常，根会话据此改派 scout 或直接完成，不得要求执行者将就。

## 约束

1. 默认异步派发并保留继承上下文，最多并行 4 个子 Agent，禁止子 Agent 再生子 Agent。
2. 子任务描述必须明确：目标、cwd、权限边界、相关文档路径、验收标准、期望输出格式、停止条件。
3. 一个 writer 一个工作目录或一个 worktree，禁止并行 writer 改动同一文件；实现与测试执行永不同段。根会话自行并行派发写入者时，**默认给每个 writer 独立 worktree**：前置条件为工作区干净，宿主对 `worktree: true` 拒脏检查，故派发前须先提交已产出的设计产物与状态件；产出是 worktree handoff 而非直接落入主树，须由根会话在主树合入，合入后重跑受影响面的机械校验；所有只读评审与验收一律读合入后的主树，不得读某个 writer 的 worktree，也不得让两个 writer 共用一个 worktree。编排脚本内的主链并行段不适用本项，因脚本在沙箱内无 git 能力，handoff 无法在主树合入，其后继节点会读不到产物；该段仍按一个 writer 一个互斥目录分域。项目非 git 仓库时退回共用工作目录，按含写入者互斥的目录分域。并行分域的交付责任两条须成对适用：他人接缝与中间态不修；本域停手交付时必须全绿，失败项先判归属，属本域者修完方可交付，属他域者须显式登记归属并报根会话，不得仅以非本域为由交付，不得把失败项整体归因于他人。
4. 子任务结果冲突时，由根会话引具体规范条款与被批驳主张裁决，不再外派独立代理。
5. 关键规则须正文内联或写入派发任务文本；pi 的 skill 机制只广告名称与描述，正文需按需读取，不得把关键规则只放在 skill 里。
6. 所有子 Agent 输出同样遵守本文件的强制中文规则与代码注释纪律。
7. 派发任务书内的检索须限定在明确目录内并带路径参数，禁止不带路径的检索与全盘扫描；单条命令超时未返回即放弃，换用更窄的检索面，不得等待。检索面之外的目标不存在属常见情形，如宿主提供的包按规范不安装，子代理不应为此探查。
8. 派发任务书须把核验落到纸面：凡任务涉及先查明实际状态再动手的事项，须在任务书中给出核验结果或核验步骤，不得只给结论。

# 代码注释纪律

1. 代码文件中的注释应克制、必要、准确：只解释"为什么这么做"，即意图、坑位依据、约束来源，不复述代码本身"做了什么"。
2. 禁止过度注释：逐行注释、显而易见的注释、大段叙述性注释、与代码重复的 docstring 皆为代码污染，不得出现。
3. 注释密度基准：公共 API、复杂算法、已知坑位必须有注释；自解释的简单实现不加注释。
4. 注释维护：修改代码时同步修订相关注释，过时注释必须删除，禁止留下与实现不符的注释。
5. 审查视角：代码评审将"注释污染"列为质量项，新增注释需问半年后的维护者是否真的需要这句话。
6. 注释只描述当前代码，不牵连过程：禁止修复史与对比叙述、轮次与编号、改动者与时间；读者只读当前代码与注释即可理解现状，过程信息属 git 历史与问题归档。
7. 文件级注释：每个源码文件头部的说明注释应说明该文件的目标与范围，即文件存在目的、承载的能力边界、不包含什么；随文件粒度拆解同步维护。
8. 替换优先于追加：改动落笔前先判断应再补一条，还是应把既有表述重写为准确的当前描述；注释块累积多条历史式补充时重写为一段当前约束说明；并列的字段与方法应合并；文件持续膨胀而职责相近时拆分或合并，不许只增不减；同一函数被反复打补丁时应重构而非继续叠加守卫。该原则适用于字段、方法、类与文件，不限注释。
9. 单一权威与声明可验证：同一规则不得多处并列定义，其余位置只留指针；任何声明必须有消费方与验证手段，无消费方的声明不得引入，已存在的一律修剪。
10. 本条为全局要求，适用于所有项目与所有子 Agent；与强制中文规则并行生效，注释内容中文但数量克制。
