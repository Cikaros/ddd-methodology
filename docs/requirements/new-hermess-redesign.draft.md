# 基于 Pi.dev 的分治式设计驱动开发方法论 · 架构概要设计（重订）

> `$Hermess = 操作系统$`
> `$pi.dev + pi.subagent + ddd.methodology = Hermess$`

**本件写作约定**：逐条标注来源——无标记者为**原概要设计原文**（逐字保留，仅调整缩进层级）；`＋ 补充` 者为本次据参考库 `hermess-engineering` 与现状 ddd 项目补入的条目。补充条目一律给出**参考出处**（`R/<文件>` 指参考库，`D/<件>` 指现状 ddd 项目），便于逐条追认或驳回。

## 一、决策与改造口

1. 项目初期、项目目标变更等重大决策上应反复迭代，深入论证后再做决定。
2. 判断时应让 agent 提供方案的优缺点和选择该方案的后续走向，最好采用效果对比视角来展示供人工判断。
3. 对外提供 Commands 改造口，以便使用者可以基于当前 ddd 项目进行适配性改造。

- ＋ 补充：**论证稿是重大决策的强制前置**。每份论证稿须含四列对比表（备选项｜证据｜代价｜后续走向），落 `docs/audits/`，登记 `docs/temp.jsonl`，裁决后清理。出处 `D/AGENTS.md`「推进纪律」。
- ＋ 补充：**证据分级**。论证稿每条论据须标注来源与强度（直接证据／转述／推断），不接受自述完成。出处 `R/01-Harness工程核心原则/05-验证、工具与优化.md`（「你改进系统的能力上限，完全取决于你验证输出有多容易」）。

## 二、三根支柱

- 设计环境
    - 知识
    - 规则
- 明确意图
- 构建反馈
    - 测试手段

分治思想是核心，文档驱动是必须，用户所有的一切都体现在文档更新中。
在修改设计方案的同时通过项目级 jsonl 等半结构化文件记录文档变化。
并在设计文档更新完毕后，统一同步落地为项目代码。

- ＋ 补充：**四路归因注册口**（把「Agent 出错」从「再试一次」变成「补缺口」）。诊断按四类分流，每类对应一种要补的件：
    - **信息缺失** → 补「可读的系统状态」：能否读到相关状态；读到了是否可解析。
    - **知识缺失** → 补「可发现的知识」：知识是否在仓库；在仓库里是否易被发现。
    - **规则被忽略** → 补「强制执行」：规则是否已成文档；文档是否已编码为可机械执行的判据。
    - **工具不匹配** → 补「工具本身」：模型能否正确使用；返回值是否结构化。
  出处 `R/01-Harness工程核心原则/速查.md`、`R/01-Harness工程核心原则/02-让Agent拥有感官.md`。
- ＋ 补充：**约束三级火箭：建议 → 文档 → 代码**（约束力弱→中→强）。同一件事只允许在这三级里选一级落点，并写明选它的理由；「文档」级必须同时声明它靠什么执行（否则等同「建议」）。出处 `R/01-Harness工程核心原则/02-让Agent拥有感官.md`。
- ＋ 补充：**Linter 即 Prompt**。机械判据的报错信息里直接写补救指令——Agent 读到报错即读到一条 Prompt，自己改到全绿。据此，**每条判据的输出必须含补救字段**。出处 `R/01-Harness工程核心原则/02-让Agent拥有感官.md`。
- ＋ 补充：**不写提示词的硬约束**。凡是机械可判定的约束，一律落守卫或校验件，不写进提示词；提示词只承担**不可机械判定**的判断式。出处 `R/01-Harness工程核心原则/02-让Agent拥有感官.md`（「文档依赖人工执行，代码瞬间全量生效」）、`D/AGENTS.md`。
- ＋ 补充：**Build to Delete**。架构须像乐高一样松散：对控制流做过度设计，会被下一次模型升级直接击穿；每一层都要能随时撕掉。作为设计评审的一条硬要求：**任何「聪明控制逻辑」须给出它的可删除边界**。出处 `R/01-Harness工程核心原则/04-Harness即操作系统.md`、`速查.md`。
- ＋ 补充：**The Harness is the dataset**。留痕不是日志，是资产：精确记录模型在第 N 步之后在哪丧失遵循指令的能力，崩溃轨迹可回灌。据此，**留痕件的字段须能回答「在哪一步、因何失守」**。出处 `R/01-Harness工程核心原则/04-Harness即操作系统.md`、`速查.md`。

## 三、四类文档形态

- 当前项目：非 ddd 项目，用户正在开发的项目。若用户正在使用 pi.dev 开发 ddd 项目，则当前项目即 ddd 项目
- 多文件形式：时间线或版本化管理
- 单文件形式：仅此一处，文档永远保持最新
- 文件树形式：仅最新版本，按照分而治之的核心思想将设计按文件路径逐步细化。主要包括**子项目级**、**模块级**、**分组级**、**文件级**
    - 全局：`docs/GLOSSARY.md`、`docs/CHANGELOG.md`、`docs/CHANGELOG.jsonl`、`README.md`、`CONTRIBUTING.md`
    - 子项目级：子项目定位与边界 `docs/<subproject>/DESIGN.md`
    - 模块级：模块项目定位与边界 `docs/<subproject>/<module>/DESIGN.md`、核心思路/协议设计 `docs/<subproject>/<module>/DESIGN-<core_name>.md`
    - 分组级：目录定位与边界 `docs/<subproject>/<module>/.../<path>/.../DESIGN.md`
    - 文件级：文件定位与边界、对外暴露接口、需引入的依赖、调用的模块能力及接口 `docs/<subproject>/<module>/.../<path>/.../DESIGN-<filename>.md`

- ＋ 补充：**单元权威与反漂移**。同一事实只允许在一处定义（记名登记：事实名 → 权威件）；其余一律引用不复写。机械判据须能**检出别处的复写**，且**权威件自身取值须等于实物**（权威件自己错时无人报是最坏情形）。出处 `D/docs/ARCHITECTURE.md`（M10 节）、`R/01-Harness工程核心原则/02-让Agent拥有感官.md`（反模式：单个巨型 agents.md → 立即腐烂成过时规则坟场）。
- ＋ 补充：**术语唯一权威**。`docs/GLOSSARY.md` 是术语唯一出处；新术语先在此补条，再在别处引用。出处 `D/AGENTS.md`。
- ＋ 补充：**宿主环境信息不入受控件**。绝对路径、主机 OS 与构建号、用户名只许写进**不入版本控制**的环境记录件；受控报告里的根一律写仓库相对形式（否则同一仓库状态在不同机器上读出不同字节）。出处 `D/docs/ARCHITECTURE.md`（C-42）、本次修复实录（每一份门禁报告都曾带着本机绝对路径进了 git 记录）。
- ＋ 补充：**扫描面与语言无关**。凡递归扫描项目的件，须按「非受版本控制的面」建跳过集（依赖、构建产物、缓存、编辑器状态）：Python 虚拟环境、前端框架产物、JVM `target`、.NET `obj`/`bin`、C/C++ `CMakeFiles` 等。跳过的清单只在一处定义，设计件不复写。出处 本次修复实录（`walk` 曾只跳 `.git` 与 `node_modules`）。

## 四、版本与临时件

- 版本管理机制：由用户决定是否启用，按照 `v<A>.<B>.<C>` 的形式进行。A 代表全局重构性变更，B 代表新需求变更，C 代表 FIX 需求变更和其他需求变更。若用户未明确要求默认版本号按 +1 处理。
- 临时文件管理机制：需要产生临时文件、文件夹时请记录至 `docs/temp.jsonl` 中，当需求完整结束到达收尾阶段时按照此记录进行清理，完成后清空 `docs/temp.jsonl`

- ＋ 补充：**版本发布是「落点多处」的机械问题**。版本的每一处落点都必须有判据证明它可达；声明的落点比判据宽，即产出「写了但没人判」的死条款。出处 `D/docs/reports/known-issues.md`（收尾要求的「版本落三处」实测第三处不可达）。
- ＋ 补充：**临时件不得登记仓外绝对路径**；登记项须为仓库相对路径，收尾以登记对账清理。出处 `D/tools/validate.js` 的 `temp` 类、本次修复实录。

## 五、需求

- 需求文档，多文件形式，由用户提供，Agent 多次调研并和用户迭代确认直至冻结 `docs/requirements/<req_type>-<req_name>.<status>.md`
    - `docs/requirements/history-requirements.jsonl` 半结构化需求历史记录，用于记录当前项目所有需求摘要

    - 需求类型：新需求、FIX 需求、其他需求

## 六、架构

- 架构文档，单文件形式，根据项目定位与边界和大致需求轮廓确定项目技术栈、核心依赖、基本目录结构、开发环境探查情况（技术栈相关工具）`docs/ARCHITECTURE.md`

- ＋ 补充：**架构文档必须自带承重机制清单**。「承重机制」＝被多个环节消费、缺失即导致整体设计失效的机制；缺失时不得以约定替代。每一条承重机制须写：它被谁消费、缺了会坏在哪里、它的机械承接是什么。出处 `R/01-Harness工程核心原则/04-Harness即操作系统.md`（四大核心功能）、`D/README.md`。
- ＋ 补充：**技术栈与校验工具链分离**。声明的是语言；工具链未就位时，对应用例报「不适用」而非缺口——否则一台未装前端工具链的机器永远走不完门禁。出处 `D/docs/ARCHITECTURE.md`「语言栈声明」节。

## 七、详细设计

- 详细设计文档，文件树形式，根据需求和架构文档构建、重构设计文件树，让文件树保持最新

- ＋ 补充：**四级同构**。`docs/<subproject>/<module>/.../<path>/...` 与仓库根同名目录一一对应；设计树的每一级都要有 `DESIGN.md`（定位与边界），文件级另有 `DESIGN-<filename>.md`。出处 原概要设计第三节；`D/docs/ARCHITECTURE.md`（C-03 同构判据）。
- ＋ 补充：**文件级设计件四个必备节**：定位与边界、对外暴露接口、需引入的依赖、调用的模块能力及接口。出处 原概要设计第三节。
- ＋ 补充：**契约冻结与落地标记**。设计件声明 `status`（draft/frozen）与 `landed`；`landed: true` 只允许出现在 `frozen` 件上——否则「已落地」可由一个未评审的草案声明。出处 `D/docs/ddd/tools/DESIGN-validate.md` 的 `landed` 类。
- ＋ 补充：**声明面与实物双向对账**（四条同族判据）：① 声明了但实物没有；② 实物导出了但设计一字未提；③ 源件在设计树里无落点；④ 引用面不可解析。出处 `D/docs/ARCHITECTURE.md`（C-36…C-40）。
- ＋ 补充：**凭空发明是最重的一类缺陷**。实测：实现者发明了一个不存在的接口签名并**蔓延五份设计件**，直到人工逐件核对才抓出。故设计件声明的签名须与实物逐字对账。出处 `D/docs/CHANGELOG.jsonl`（CHG-0065）、`D/docs/reports/verify-findings.md`。

- 测试用例设计文档，文件树形式，与详细设计文档结合

- ＋ 补充：**编号须全局唯一**。实测同一编号在数十处被不同件复用，导致「落地判据」假阴性：本件未落地的用例被另一件的测试冒充成已落地。出处 `D/docs/reports/known-issues.md`（用例编号跨件重名）。
- ＋ 补充：**用例件的引用面可解析**（执行件／前置件／夹具所引的仓库路径须实存），但**期望值的对错不可完全机械化**，须单列人工校对面。出处 `D/docs/ARCHITECTURE.md`（C-40）。
- ＋ 补充：**评估金字塔与纵深防御**（作为测试手段的总纲）：代码评分器 80% ＋ 模型评分器 15% ＋ 人类评分器 5%；选择原则「能用代码不用模型，能用模型不用人」。四层纵深：代码（全覆盖、同步拦截）→ 模型（抽样 10–20%）→ 规则引擎 → 人类（关键节点）。**门禁＝全覆盖同步拦截那一层；评估＝抽样异步度量**——二者须显式分开，不得混用。出处 `R/06-Agent评估/02-评分器体系.md`、`R/06-Agent评估/03-四类评估与纵深防御.md`。
- ＋ 补充：**统计判据成对报告**。`Pass@k` 测能力上限、`Pass^k` 测可靠性下限，两者同时报告。出处 `R/06-Agent评估/01-为什么需要评估.md`。
- ＋ 补充：**评估漂移自省**。通过率方差趋近零说明评估失效；模型升级后须人工抽检。出处 `R/06-Agent评估/03-四类评估与纵深防御.md`。

## 十二、门禁、测试、版本与项目的对接（本件最要紧的一条）

> 原概要设计第 3 条「对外提供 Commands 改造口」的推广：**门禁也该是改造口**。
> 门禁规则它应该是指定了一种规范，任何项目都有其不同的门禁，但对于特定项目来说只需要将项目门禁按照特定的规律对接给 ddd 框架即可。我想很多地方其实都是类似的思路，比如测试、版本机制等，ddd 只为让项目更加准确无误的实现，并不是为了限制项目的发展。

据此，新设计取如下定调（＋ 补充，待裁决）：

- **规范与实现分离**。方法论定义**对接规范**，并只自带一套**缺省实现**；项目按规范登记自家的门禁／测试／版本落点，框架负责校验其形态、接入读数、进入节点源与留痕。
- **对接规范的最小字段集**（每道门禁一条）：`id` / 判面（判什么、不判什么）/ 执行者 / 读数形态 / 完成判据 / 失败语义（阻塞·可见·仅留痕）/ 是否入节点源。
- **登记面必须自省**。每道门禁（无论缺省还是项目登记）须自报：判面、判定对象数、未识别形态数；且**「零 FAIL」与「无判定对象」必须是两个读数**。否则「登记了但没在判」与「登记了且在判」在读数上不可分——不一致只会从方法论搬到项目里。出处 本次实测（不拦的检查等于零）、`D/docs/ARCHITECTURE.md`（C-41）。
- **两套主体不混用**。**贡献者面**（保证分发的配置正确：形态校验、引用完整性、跨平台兼容）与**使用者项目面**（保证按需装入：声明所需组件、选预设）须分开，不得混用同一份判据。出处 `R/08-ECC教程/09-工程基础设施.md`、`R/08-ECC教程/08-跨Harness适配.md`。
- **按需装入**。以 **Manifest**（本项目需要哪些组件）＋ **Profile**（预设套餐）声明，避免装入不需要的组件产生上下文噪音。出处 `R/08-ECC教程/08-跨Harness适配.md`。
- **约束落在最便宜处**。成本函数已反转：**修正便宜、等待最贵**。故门禁的第一选择是「自动检查 + 快速反馈」，而非「等人批准」；确实需要人判的，必须标明它阻塞什么、阻塞多久。出处 `R/01-Harness工程核心原则/03-成本、自主与熵增.md`。
- **失败语义三分**（沿用并扩为规范）：`阻塞`（不通过即拦下，须给补救）/ `可见`（读数入册但不拦）/ `不适用`（判定对象不存在，退出码零）。**「不拦的检查」不得渲染成「全通过」**。
