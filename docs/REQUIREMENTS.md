# 需求：基于 OpenCode Plugin 的分治式设计驱动开发方法论

> `$Hermess = 操作系统$`
> `$opencode-plugin + subagent + ddd.methodology = Hermess$`

本件是本方法论（Hermess 2.0）的**需求基线**，宿主为 **OpenCode**。设计见 `docs/OUTLINE-DESIGN.md`；术语以 `docs/GLOSSARY.md` 为准（由本方法论初始化时生成）。

本件结构：一、定位；二、适用场景；三、目标与非目标；四、需求条目（R1–R64，每条含可判定线索）；五、需求剪裁；六、补充需求；七、裁决记录；八、验收线索。

---

## 一、定位

- 本方法论**产出的是环境，不是功能**。使用者装入后，在当前项目根搭起设计文档骨架，其后按节点序列与门禁推进**当前项目**。
- 定位依据：`Model × Harness = 最终能力`。模型能力决定上限，本方法论（Harness）决定逼近上限多少。
- 等式：`opencode-plugin + subagent + ddd.methodology = Hermess`。
- **当前项目**：使用者正在开发的那个项目。判定面是「当前项目根是否存在本方法论的骨架与判据件」，**与宿主名无关**。

## 二、适用场景（三类）

本方法论须服务三类场景；场景**不改变**骨架与门禁，只决定**入口节点、步子大小、以及有无一次例外**。

### 场景一 · 项目从零开始选型实现

- 特征：无既有代码、无既有设计树。
- 入口：`/ddd-init` → `/ddd-intent` → `/ddd-arch`（选型）→ 全节点序列。
- 特殊：**选型是重大决策**，须先出书面论证稿再定；设计树自顶向下建。门禁 G1–G6 全走。

### 场景二 · 二次开发类项目

- 特征：已有项目与（可能部分的）设计树；工作是**追加功能、追加接口、修改 bug**；在特定场景/框架下 **Todo 驱动**。
- 入口（按需求类型分流）：追加功能/接口 = 新需求 → `/ddd-intent` → `/ddd-design` → `/ddd-implement` → `/ddd-test`；修 bug = FIX 需求 → `/ddd-change` + 最小设计更新 → `/ddd-implement` → `/ddd-test`。
- 特殊：**Todo 驱动**——每个 Todo 是一条**看板任务**（须带 `acceptance`）；设计更新须**外科式**，只动受影响节点。门禁以 G3/G4/G5 为主。

### 场景三 · 项目迁移

- 特征：项目已存在（甚至语言/框架要换），**设计树不存在**。
- 特殊——**方向反转一次**：正常是「先文档后代码」；迁移期须先由既有代码**反推**设计树。反推件为**一次性产物**，标 `status: draft`（**不得直接 `frozen`**），且**必须可机械对账**（声明面与实物双向）；核对后回到正向流程。
- 入口：`/ddd-init` → `/ddd-design --from-code` → `/ddd-arch` 校验 → 其后同场景二。

### 场景对照

| 维度 | 场景一 · 零起 | 场景二 · 二次开发 | 场景三 · 迁移 |
|---|---|---|---|
| 设计树 | 无 → 自顶向下建 | 有（可能部分）→ 外科式更新 | 无 → 由代码反推 |
| 入口 | `/ddd-init` | 新需求 或 FIX 入口 | `/ddd-init` + 反推 |
| 驱动 | 节点序列 | **Todo 驱动**（看板任务） | 反推 + 节点序列 |
| 例外 | 无 | 允许外科式、允许部分树 | **允许一次「代码 → 文档」反向** |
| 主导门禁 | G1–G6 | G3 / G4 / G5 | G3（反推同构）+ G1–G6 |

- 三者**共用同一套骨架与门禁**，差异只表达为「选走哪些节点」，**不得为某场景写死路径**。

## 三、目标与非目标

| 项 | 内容 |
|---|---|
| **目标** | ① 一套可机械校验的设计驱动开发流程（设计树 / 测试树 / 变更流 / 门禁）；② 一个可装入 OpenCode 的插件包，提供命令、技能、代理、规则、守卫与报告；③ 对外可对接的改造面（命令、门禁、测试、版本）；④ 知识、规则、反馈三态的沉淀与复用；⑤ 服务三类使用场景。 |
| **非目标** | 不产出业务功能代码；不产出数据库与后端服务；不产出前端界面；不做模型选型与推理参数调优；不接管宿主的会话存储；不规定使用者项目的业务架构。 |
| **交付判据** | 交付的是「**缺陷已全部登记**的设计」，不是「无缺陷的设计」。 |

| 编号 | 需求 | 可判定线索 |
|---|---|---|
| R42 | **冻结即归并**：需求、设计、代码三者冻结时，各做一次**最终版优化转换**——剔除产物内联的**变更记录痕迹**（如 `CHG-####`、「本次修订」「原为 X 现为 Y」、`draft` 标记、废弃节），把产物**重构成最终形态**（而非在旧文上继续打补丁） | 冻结件内联痕迹零残留（机械可检）；归并前后契约逐字对账 |

| R45 | **归并留痕但不内联**：每次归并写一条变更流（`type: docs`），使归并**可审计**而**不写入产物正文** | 变更流存在对应归并记录；产物正文无该记录 |
| R63 | **冻结点即 git 检查点**：每个冻结点（需求冻结／概要设计冻结／设计树冻结／代码冻结）都须做一次 **git 本地提交**作为检查点，便于回溯与追溯；提交须可定位到该冻结版本 | 每个冻结点存在对应本地 commit；`git log` 可回溯到该冻结状态；工作区在提交后干净 |

### 丑、前端：变体契约奠基（第 0 步）

> **定位**：在 UI 生成之前，把「合法变化空间」枚举穷尽、量化封顶、写入**机器可读契约**，使后续所有生成被限制在**有限且可枚举的设计空间**内。它**不是**另立一套前端体系，而是 ddd 的一个**随包技能** + 一个**项目登记门禁**，挂接在既有节点序列与对接规范上。

**磨合边界（与原设想的差异，逐条剔除不兼容部分）**：

| 原设想 | 与 ddd 冲突 | 采纳形态 |
|---|---|---|
| 项目根 `DESIGN.md` 变体段 | 违反根文档白名单（R12） | 变体段落 **`docs/ARCHITECTURE.md`** |
| 独立 `variant-contract.json`（位置未定） | 需固定位置 + 单点权威（M10） | **`docs/variant-contract.json`**（项目级单点权威） |
| `theme-config` 作输入源 | ddd 派生物由重放生成、禁手改 | `theme-config` 改为**派生件**（由契约重放） |
| 写 `CLAUDE.md`/`.cursor/rules` | 仅 OpenCode，只认 `AGENTS.md` | 只落 **`AGENTS.md`** + 技能 references |
| 硬前置「5 步约束体系」 | 本仓无此体系 | 可选对接，非前置；挂 `/ddd-arch` |
| lint/CI 内建变体检查 | ddd 内置门禁只判 ddd 文档 | 变体审计 = **项目登记门禁**（R28 七字段） |

| ≤3 维度 / 上限 2 作硬法则 | ddd 不规定前端取值 | 降为**默认建议＋代价**，可改 |

### 寅、零手动提示的自主注入与底线守卫（核心诉求）

> **核心诉求**：使用者**不必手动提示 skill 等信息**，而由插件**自主抉择注入合适内容**引导 agent；同时**守好底线，不被 agent 带偏**。
> 两层必须分开：**注入是引导**（可删、可被绕过）；**底线是机械强制**（绕不过）。混为一谈即失效。

| 编号 | 需求 | 可判定线索 |
|---|---|---|
| R52 | **零手动提示**：使用者无需 `@skill` 或敲命令加载纪律；插件据当前上下文**自主注入**合适内容 | 不输入 skill 名/命令时，纪律与知识仍被注入；注入有留痕 |
| R53 | **两层分离**：注入层＝引导（可删、可绕过）；守卫层＝底线（机械强制、绕不过）。**能机械判定的底线绝不只写进注入文本**（§三.7） | 底线有机械落点；注入文本不承担机械判定 |
| R54 | **自主判定**：判据＝命令相位（`/ddd-*`）＋ `prompt` 意图（文本/附件）＋ 场景（三类）；据此选**最小切片集**；判定依据可观测 | 相位/意图/场景可判；注入的 `sliceId` 与依据入留痕 |
| R55 | **幂等注入、不占轮次**：经 `session.hook("context")` 与 `ctx.session.instructions.entry`（**键控**）；同一键重复写是更新，不重复注入；不产生对话轮 | 同一步不重复注入同一片；注入不进对话轮次 |
| R56 | **渐进式披露**：只注入**最小切片**；全文留 `skills/**/references/` 按需读 | 注入量有上限；全文非常驻 |
| R57 | **底线机械强制**：每条底线声明**执法点**（permission `deny` / tool hook / gate block）；**落不进执法点的不是底线** | 每条底线有机械落点；无执法点者不入底线清单；失败带 remedy |
| R58 | **注入与守卫自省**：注入自报（几片/哪些 id/依据）；守卫自报（拦住几次/未识别几次）；**「零违规」与「无判定对象」是两个读数** | 两者均自报；两读数可分 |

> **诚实边界**：不追求「全自动读懂意图」。追求的是——**相位确定时注入确定内容 + 底线机械兜底**；判定误判只影响引导（可删），不损坏底线（机械）。

### 卯、语言规范与工具使用规范（随包技能）

> **定位**：知识层的**语言规范**与**常用开发工具使用规范**技能。**机械取值**（缩进、行宽、分号、格式化选项）落 `assets/` 单点权威并由宿主 formatter/linter 消费；技能正文只放**不可机械判定的约定**。上游风格指南**只引用、不拷入**（哈希绑定其版本）。

| 编号 | 需求 | 可判定线索 |
|---|---|---|
| R59 | **语言规范技能族**：覆盖常用语言——**html、css、js、vue、java、python、shell（sh/zsh/bash/pwsh）、android、sql（mysql/redis）、c、c++、nasm**；每语言一技能 `skills/lang/<id>/`，**默认采用对应的 Google 风格指南**（无对应者用该语言官方/事实标准）为基线，项目可覆盖 | 目录清单与 `assets/languages.json` 逐条对应；每语言声明基线来源；覆盖可登记 |
| R60 | **工具使用规范技能**：与上述语言**相关的常用工具/命令**的使用约定落 `skills/dev-tools/references/`（如 git、包管理器、构建（maven/gradle/javac、pip/venv、npm/pnpm、gcc/g++/make、nasm、adb/gradle）、formatter/linter、测试运行器、CI、容器、shell 内建、`mysql`/`redis-cli` 等）；只写**用法与判断** | 工具清单覆盖各语言的常用链路；每条约定非机械取值复制 |
| R61 | **机械值落 assets**：语言的**可判取值**（缩进、行宽、引号、尾逗号、严格度等）只在 `assets/lang-<id>.json` 写一次，由项目 formatter/linter 消费；技能只引用 | 技能正文无具体阈值；assets 与工具配置一致 |
| R62 | **按需注入**（与 R52 联动）：语言/工具技能**不常驻**；插件据检测到的语言/工具**自主注入**对应切片 | 未检测到某语言时其切片不注入；注入留痕可读 |

> **族与实例**：`skills/lang/<id>/` 是**同构实例**——共享同一模板（`skills/lang/DESIGN-SKILL.md`）与同一目录（`assets/languages.json`）；因此族设计件 + 目录资产即覆盖全部语言，逐语言另立完整设计树会与「单点权威」冲突并被判冗余。工具规范同理。

> **取舍**：Google 风格指南是**默认基线**而非硬法则；与项目既有约定冲突时以项目为准，并在项目侧登记覆盖理由（避免"基线 vs 项目"两处打架）。宿主已提供 formatter/linter（§十六），本技能**不重造**，只提供约定与配置基线。
