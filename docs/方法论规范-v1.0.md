# 分治式设计驱动开发方法论规范 v1.0

标题补充说明：本规范即 DDD-Methodology。

> **本文为历史定稿快照，不再同步更新。** 唯一演进版为 skill/ddd-methodology/references/spec.md；变更历史见 CHANGELOG.md。
> 实现形式：pi Skill 加 pi-subagents 自定义 agent 定义为主方案，Workflow 脚本为可选加速档。

## 1. 核心理念

**分治式设计驱动开发**：文档随架构分治、上下文随职责分治、缺陷随层级路由。

**问题根源**：传统大设计文档使子代理会话记忆负担过高，实现逐渐偏离设计。
本质是**上下文与职责不匹配**——实现者被迫加载不属于自身职责的信息，稀释了对关键设计的注意力。

三个基本原则如下。

1. **上下文最小化原则**：每个代理只加载与其职责和当前任务直接相关的文档，禁止整卷加载；实现者默认就近加载，但**允许按需上溯父级与更高层设计文档**获取设计理念，防止实现片面。
2. **文档跟随架构原则**：设计文档不是一卷，而是一棵与目录结构同构的文档树；每个有实现内容的目录一份 `DESIGN.md`，纯结构目录并入父级文档。
3. **缺陷层级路由原则**：缺陷默认按最低层判定，自检通过仍失败则上移一层；定级争议由根会话仲裁，必要时升级用户。

## 2. 代理职责链

```
用户 ⇄ 根会话（调度 + 验证 + 缺陷定级仲裁）
              │
   代理1 需求采集者 ⇄ 用户确认对齐
              ↓
   代理0 验收标准制定者（总 AC → 分发模块级 AC）
              ↓
   代理2 架构师（新建：技术环境+目录规划 / 二次开发：现状分析→对齐原准则）
              ↓
   代理3 分解设计者（目录级 DESIGN.md 文档树）
              ↓
   ┌──────────┴──────────┐
   代理4 实现者（就近加载实现）   代理5 测试规划者（总AC+模块AC→测试计划）
   └──────────┬──────────┘
              ↓
   代理6 测试执行者（按计划执行 → 缺陷四级路由闭环）
```

### 代理定义

| 代理 | 职责 | 关键约束 | 核心产出 |
|---|---|---|---|
| **根会话** | 调度全链路、按总 AC 验证、缺陷定级仲裁 | 不直接实现；仲裁争议时升级用户 | 验证结论、调度决策 |
| **代理1 需求采集者** | 对模糊需求提问与推导，与用户反复确认直至对齐；判定项目类型为新建或二次开发 | 未对齐前禁止放行 | `REQUIREMENTS.md`，含项目类型判定 |
| **代理0 验收标准制定者** | 将需求转化为 Given/When/Then 可执行验收清单；拆分模块级 AC 并分发到各 `DESIGN.md` | 总 AC 留根会话，模块级 AC 就近存放 | `AC.md` 总清单，加模块级 AC |
| **代理2 架构师** | 新建：确定技术环境与目录规划，符合该语言大众编排习惯；二次开发：**先现状分析**，仅当项目缺少规范文档时执行，提炼原有准则 | 二次开发新模块必须与原结构同构 | `ARCHITECTURE.md` 加目录规划，缺规范文档的二次开发另含现状分析报告 |
| **代理3 分解设计者** | 复杂功能分解设计；为每个有实现内容的目录产出 `DESIGN.md`，含能力范围、接口、依赖约束、模块级 AC | 纯结构目录并入父级文档；文档树与目录同构 | `docs/design/` 文档树 |
| **代理4 实现者** | 按就近 `DESIGN.md` 实现，可上溯高层文档获取设计理念 | 禁止整卷加载；按设计实现，发现设计问题走 B 级路由而非自行改设计 | 各目录代码 + 单元测试代码 |
| **代理5 测试规划者** | 基于总 AC、模块级 AC 与设计文档制定单元测试计划 | 计划与设计文档树同构、就近存放 | `TEST_PLAN.md`，树状分布 |
| **代理6 测试执行者** | 按计划执行测试，对失败项定级并路由 | 默认最低层定级，自检通过仍失败才上移 | 测试报告 + 缺陷路由单 |

## 3. 缺陷四级路由

| 级别 | 定义 | 判定自检问题 | 处理代理 | 产出 |
|---|---|---|---|---|
| **A 需求级** | 设计无法满足需求，或需求本身矛盾/缺口 | 设计正确执行后能否满足 AC？ | 代理1 → 用户确认 | 修订的需求/AC |
| **B 设计级** | 设计缺陷、边界不清、接口矛盾 | 设计是否自洽、可实现？实现者是"做不出来"而非"没做对"？ | 代理2/3 修订设计，同步修订 AC | 修订的设计文档 |
| **C 实现级** | 设计正确但实现偏离设计 | 代码与设计文档哪里不一致？ | 代理4 修码 | 修复代码，不改设计 |
| **D 测试级** | 测试计划本身错误，如漏场景、错断言、覆盖缺口 | 计划是否遗漏场景、断言是否错误？ | 代理5 修计划，代理6 重跑 | 修订计划加重跑报告 |

**判定规则**：从最低层 C/D 开始判定，自检通过仍失败则上移一层；**小缺陷就地修复，仅 B 级及以上才回设计层**。定级争议由根会话仲裁，必要时升级用户。

## 4. 回路终止条件

同一缺陷轮回修复超过 **2 轮**仍未解决 → 强制升级用户决策，禁止继续无效循环。

## 5. 文档体系

```
项目根/
├── REQUIREMENTS.md            # 代理1 产出（含项目类型判定）
├── AC.md                      # 代理0 产出（总验收清单）
├── ARCHITECTURE.md            # 代理2 产出（含横切规范：日志/异常/命名等）
├── CONVENTIONS.md             # 可选：横切规范独立成文（5 采纳）
├── docs/design/               # 代理3 产出：与目录结构同构的文档树
│   └── <模块>/<子模块>/DESIGN.md
└── docs/test/                 # 代理5 产出：与设计树同构的测试计划树
    └── <模块>/TEST_PLAN.md
```

DESIGN.md 模板字段，对应已采纳的决策点 3：职责描述、能力范围做与不做、对外接口约定、依赖约束、模块级验收要点、变更记录。

横切关注点，对应已采纳的决策点 5：日志、异常处理、命名规范等横切规范集中一份，置于 `ARCHITECTURE.md` 或 `CONVENTIONS.md`，模块文档只写差异点，避免 DRY 违背。

就近加载加上溯，对应已采纳的决策点 4：实现者默认就近加载对应目录 `DESIGN.md`；当模块行为需要更高层设计理念支撑时，允许上溯父级 `DESIGN.md` 与 `ARCHITECTURE.md` 相关节选，防止实现片面。

二次开发现状分析，对应已采纳的决策点 9：仅当二次开发项目**缺少**自身规范或设计文档时，代理2 才执行现状分析并输出报告；项目已有规范文档、仅切换会话的情形不符合二次开发定义，直接对齐现有文档。

## 6. 实现形式

实现形式对应已确认推荐的决策点 7。

1. **Skill**：方法论规范主文档与 references 模板库，根会话加载后按规范调度；
2. **Agent 定义**，位于 `.pi/agents/*.md`：7 个代理的 frontmatter 硬约束，包含工具白名单、模型档位、输出契约、停止条件；
3. **Workflow 脚本**，可选加速档：固定阶段 1→0→2→3→4/5→6 自动推进；默认由根会话手工调度，保留缺陷仲裁灵活性。
