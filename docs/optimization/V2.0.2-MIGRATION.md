# 从 2.0.1 升级到 2.0.2

2.0.2 是联动与可靠性改造，不是命令层面的破坏性升级。15 个命令、12 个 Agents、33 个 Skills 不变；根本目标仍是文档驱动和证据验收。

## 建议升级步骤

1. 备份当前项目的 `docs/`、`.opencode/` 和 `.ddd/state/`（若存在）。尤其不要丢失已存的工作流事件及看板日志。
2. 解压 2.0.2 到新的独立目录，不要把压缩包直接覆盖进已有插件目录。
3. 使用 Node.js >=22.19.0，在插件源码根执行 `npm ci && npm run check && npm run typecheck && npm test`。
4. 在用户业务项目运行只读预检：

   ```bash
   node /path/to/ddd-methodology-2.0.2/scripts/materialize.mjs all --root /path/to/project --check
   ```

5. 预检无冲突后执行物化：

   ```bash
   node /path/to/ddd-methodology-2.0.2/scripts/materialize.mjs all --root /path/to/project
   ```

6. 如果提示用户现有文件与随包内容不同，**不要直接使用 `--force`**；先逐一比较内容，决定保留自定义文件还是更新。只有确认需要覆盖时才显式使用 `--force`。
7. 在实际 OpenCode 中测试 `/ddd-init`、Skill 按需读取、子 Agent 评审、工作流状态、RPC/TUI 和一次真实验收。

## 迁移行为

- 新增持久会话索引 `.ddd/state/sessions/<会话 ID 哈希>.json`；没有已有子会话关联时会正常从空状态开始，不自动猜测旧会话归属。
- 提示词相关 Skill 命中保留为任务线索，项目文件/依赖变化后会重新识别当前生态。
- 上下文读取故障会显示为诊断；如果检查点损坏，会保守过滤有副作用的工具，需人工修复，而不是默默放行。
- `materialize` 和 `/ddd-init` 采用统一预检；不同内容冲突会显式失败，避免部分初始化。
- 外部发布钉版（npm/git tag）：`package.json` 与变更流已声明 2.0.2；正式发布后即可按 `@2.0.2` 或 `#v2.0.2` 修改业务项目的插件来源。

## 非自动化边界

不自动修改用户业务代码、冻结设计或发布记录；不自动删除旧状态目录；不自动重复运行存在副作用的工具；不自动开启或覆盖 DeepSeek API 参数。真实宿主安装和 API 结果需要环境内验证。
