# 代理改造契约

对象文件：`agents/` 下 12 个 `ddd-*.md`。本文是改造的冻结契约。

## 1. 通用改写规则

1. **骨架保持**：七个一级标题依次为角色、输入、输出契约、职责、硬约束、内联规则、停止条件，不得增删。frontmatter 字段保持现状。
2. **内联自足**：代理完成本职所需的判据必须在提示词内。跨文件引用只用于权威细节，且必须采用语义化形式，禁止写裸 `§N`。
3. **副本收敛**：同一规则若已有权威位置，本处只保留完成本职所需的最小判据，并标注权威位置；不得复述权威位置的全部展开。
4. **禁止暗示顺序**：需顺序处写编号步骤。
5. **中文行文**：标题无破折号与括号补充，正文避免非必要括号补充。

## 2. 统一模板

### 2.1 派发前提段

五个写入类代理的派发前提统一为下列模板，只替换方括号内容。

```
- **派发前提**：只承接[本代理产出物]。任务缺少[必需前置输入]时，停止并报告「派发类型不匹配」，注明缺失项，不得改以[禁止的活动]推进。
```

各代理取值如下。

| 代理 | 产出物 | 必需前置输入 | 禁止的活动 |
|---|---|---|---|
| ddd-decomposer | 分解设计与 DESIGN 修订 | ARCHITECTURE 与 AC | 调研或实现 |
| ddd-implementer | 按冻结契约实现代码与单元测试 | 就近 DESIGN 路径或冻结契约 | 调研、探查、方案比选、环境勘察 |
| ddd-test-planner | 测试计划 | AC 与 DESIGN | 实现或测试执行 |
| ddd-tester | 测试执行与缺陷定级路由 | 测试计划与已过 G5-INT 的信号 | 实现与修复 |
| ddd-fixer | 缺陷修复与集成收口 | 缺陷路由单或集成失败证据 | 设计变更与全量测试 |

ddd-test-planner 与 ddd-tester 若现文已含等价表述，改写为该模板；若原缺，补齐。

### 2.2 结构治理回执句

在 requirements、acceptance、architect、decomposer、test-planner 五个代理的输出契约中，回执句统一为逐字一致的一句：

> 并附结构治理回执，记录被触碰文件的改动前后规模、是否拆解与依据的粒度预判。

implementer 与 fixer 的回执句统一为：

> 结构治理回执记录被触碰文件的改动前后规模、是否拆解与依据的粒度预判，空节不得声明完成。

## 3. 逐代理契约

### ddd-requirements.md

2. 「默认解释仅适用于不影响架构与验收的细节」改为二分判据，固定表述：「可默认的细节指不影响目录规划、横切规范与 AC 判定的表述。影响其一者必须向用户提问。」
3. 输出契约补入 2.2 的回执句。

### ddd-acceptance.md

1. 跨节引用语义化。
2. 输出契约补入 2.2 的回执句。
3. 保留双向可追溯矩阵要求。

### ddd-architect.md

1. 跳转 spec 的改造分级改为内联精简表加指针。内联表三列：级别、范围、处理，取 L1 至 L5 五行，表后一句「分级入口与起评规则见「渐进式改造」节」。
2. 「已有则直接对齐，不做现状分析；缺少才做现状分析」拆为编号分支：

```
1. 项目已有规范文档时，直接对齐，不做现状分析。
2. 项目缺少规范文档时，做现状分析，输出结构推断、原有准则提炼、同构约束清单与风险坑位。
```

3. 「消费方为空的能力不得独立成文件」保留为独立判据条，与基础能力清单并列。
4. 输出契约补入 2.2 的回执句。
5. 改造影响评估按 templates 的改造影响评估表逐条填写，行标识为新功能，须含改造级别、改造内容、是否涉及冻结接口与存量债务承接级别四列，不得简化为三列。

### ddd-decomposer.md

1. 契约指纹算法保留内联，表述固定为：「取契约表内容哈希前八位」。同句补指针：「算法唯一权威见「结构与契约的演进治理」节的契约指纹条」。
2. 文档粒度阈值引用须与 spec §4 的阈值锚点逐字一致，即「代码文件 500 行、基础或核心模块 300 行、文档 200 行或 10 项契约」。
3. 派发前提改用 2.1 模板。
4. 输出契约补入 2.2 的回执句。
5. 「同构场景达 3 个」与「超 200 行或 10 项契约」保持，与阈值锚点对齐。

### ddd-interface-reviewer.md

1. 九项检查改为判定表，四列：检查项、判据、不通过时的结论、备注。九项依次为能力覆盖、能力重复、能力缺口、依赖方向、契约质量、接口粒度、独立性声明、消费方声明、契约指纹。
2. 结论列取值限定为 `fail`、`conditional`、`pass`。任一 `fail` 项命中即 `VERDICT: fail`；无 `fail` 而存在 `conditional` 项即 `conditional`；其余为 `pass`。表末增加默认行：「九项均无命中时取 pass。」
3. 反向抽查下限保留 3，并补依据句：「下限取 3，按「声明面可验证与修剪」节的反向抽查要求。」
4. 输出契约中的 VERDICT 行格式保持 `VERDICT: pass|conditional|fail`。

### ddd-implementer.md

1. 派发前提改用 2.1 模板。
2. 「预判未涵盖且无法拆解方停止并报告」拆为两条独立判据：

```
1. 预判涵盖拆解方案时，按预判执行，不得超出。
2. 预判未涵盖且确实无法拆解时，停止并报告，附两条依据：预判未涵盖、已尝试的拆解方向。
```

3. 结构治理义务保持为本代理的实体定义之一，回执句改用 2.2 第二式。
4. 单文件阈值表述与 spec 阈值锚点逐字一致。
5. 「全量测试的唯一主体是 ddd-tester」逐字保留。

### ddd-test-planner.md

1. 派发前提改用 2.1 模板。
2. 桩化规则改为触发清单加处置表。触发清单列出网络、长循环、大数据量、外部服务、真实等待五项。处置表两列：情境、处置，取值为桩化、移入手动测试清单两种，并写明「处置为移入清单时须写清原因与手动步骤」。
3. 输出契约补入 2.2 的回执句。
4. 「覆盖正常、边界、异常与依赖约束违反四类路径」改为四行编号清单。

### ddd-tester.md

1. 四级判据改为内联精简表，三列：级别、定义、处理。取值与 spec「缺陷四级路由」节一致。表后一句：「未命中任一级特征时，默认取最低适用级别。」
2. 自检顺序改为编号步骤，采用 spec「缺陷四级路由」节的五步表述。
3. 「先内层后外层，失败即定位到最小能力域再扩大」改为编号步骤。

```
1. 先验证最小能力域的内层用例。
2. 内层通过后逐层向外扩大范围。
3. 失败即停在该层，不再扩大。
```

4. 指纹比对置于编号步骤首位：「第一步比对契约指纹。指纹不变即重构，指纹变化即行为变更。」
5. 桩化与超时处置并入四级判据表：
   - 未桩化的高风险用例超时，取 D 级。
   - 因实现缺陷导致的死循环或超时，取 C 级。
6. 「全量测试的唯一主体是 ddd-tester」逐字保留。
7. 派发前提改用 2.1 模板。
8. 本文件若现有第八个一级标题「启动前置条件」，将其内容并入「输入」节首句，保持七个一级标题骨架。

### ddd-fixer.md

1. 派发前提改用 2.1 模板。
2. 结构治理义务改为指针，固定表述：「结构治理义务同 ddd-implementer 的硬约束，范围、判据与回执格式一致。」
3. 回执句采用 2.2 第二式。
4. 「禁止重复任务中已列出的失败方案」改为编号步骤首位：「第一步读取任务中的已尝试方案。第二步选择与全部已尝试方案不同的实现路径。」
5. 「全量测试的唯一主体是 ddd-tester」逐字保留，并补「本代理在集成收口与修复段均不执行全量测试」。

### ddd-arbiter.md

1. 四级判据改为与 ddd-tester 同构的精简表，三列：级别、定义、处理。两处表格内容须逐字一致。
2. 自检顺序引用同一五步表述，写为「按「缺陷四级路由」节的五步自检流程复判，默认最低层」。
3. 保留 C 与 B 的区分点，并入表外一句，固定表述：「C 与 B 的区分点在于：代码能写但不符设计是 C 级；按设计做不出来是 B 级。」
4. 派发前提补 2.1 模板一行，产出物为仲裁裁决单，必需前置输入为争议缺陷与双方定级依据。

### ddd-doc-sync.md

1. 十项巡检清单改为表，四列：巡检项、权威位置、判据、不通过时的归类。权威位置用语义化引用，禁止裸 `§N`。巡检项「规范章节索引」的判据不得包含 spec 无目录节的对象，改为核对 spec 各节标题、SKILL 步骤标注与模板章节名三者一一对应。
2. 巡检项按权威位置排序，使 Agent 自上而下读即可，无需回跳。权威位置为 `spec` 节标题或文件路径。
3. 反向抽查下限保留 3，补依据句与 interface-reviewer 同构。
4. 输出契约与报告格式保持。
5. 本文件是跳转最密集者，改造后其正文中的文件路径引用总数须下降，同一权威位置只出现一次。
6. 硬约束补一条机械证据义务：运行 `node scripts/ref-check.js .` 并附输出，使 `ref-check` 的门禁地位声明获得真实消费方。

### ddd-auditor.md

1. 声明面对象改为判定矩阵。行取九类对象：接口契约、公开导出、能力清单、规则条款、配置项、模板字段、依赖项、变更记录声称、契约指纹与变更类型声明。列出四类结论：有效、无消费方、消费不正确、纸面消费方。
2. 矩阵后给出判定顺序，编号步骤：

```
1. 判有无消费方。无消费方即结论为无消费方。
2. 有消费方时判消费是否正确。不正确即结论为消费不正确。
3. 消费正确但验证手段仅为纸面时，结论为纸面消费方。
4. 三者均不成立时结论为有效。
```

3. 证据源映射改为表，三列：核验项、证据源、判据。证据源包括 `docs/health.json`、`code-health` 脚本输出、变更记录、契约指纹，并补一行文档粒度核验，即各 DESIGN 的文档规模与契约数，判据为超 200 行或 10 项契约时须已拆解或有接受理由。该行使阈值承载表中文档两档获得真实消费者。
4. 反向抽查下限保留 5，补依据句：「全量审计对象数多，下限取 5。」
5. 归档建议名格式保持，并保留「落盘由根会话执行」。
6. 运行时契约类声明的例外保留为独立条款。

## 4. 跨代理去重对照

改造后，下列规则只允许一处实体定义，其余为最小判据或指针。

| 规则 | 实体定义位置 | 其他位置的处理 |
|---|---|---|
| 缺陷四级判据 | spec「缺陷四级路由」节 | tester 与 arbiter 内联同构精简表 |
| 契约指纹算法 | spec 16.1 | decomposer 内联哈希前八位加指针 |
| 结构治理义务 | ddd-implementer 硬约束 | fixer 写指针 |
| 结构治理回执句 | 本文件 2.2 | 各代理逐字使用 |
| 全量测试唯一主体 | spec「实现与测试分离」节 | implementer、fixer、tester 逐字内联 |
| 粒度阈值数值 | spec §4 阈值锚点 | 各代理逐字内联 |
| 反向抽查下限 | spec「声明面可验证与修剪」节 | 各代理内联数值加依据句 |
| 派发前提模板 | 本文件 2.1 | 五个写入代理套用 |
