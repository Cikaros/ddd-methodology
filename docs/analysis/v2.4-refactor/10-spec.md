# spec 改造契约

对象文件：`skill/ddd-methodology/references/spec.md`。本文是该文件改造的冻结契约，实施时逐条满足，不得增删节。

## 1. 目标形态

改造后节序如下，节标题为冻结值，其他文档引用时须逐字匹配。

```
0. 问题与解法
1. 角色与交接
2. 质量门禁
3. 缺陷四级路由
4. 粒度与独立性
5. 接口先行与冻结
6. 并行实现与集成
7. 实现与测试分离
8. 测试阻塞防护
9. 需求变更
10. 二次开发
11. 渐进式改造
12. 声明面可验证与修剪
13. 结构与注释的机械证据
14. 本仓库适用边界
15. 状态文件
16. 结构与契约的演进治理
```

## 2. 通用改写规则

1. 全部跨节引用由 `§N` 改为语义化形式，即 `见「节标题」节`。节号可附于其后。`ref-check` 校验引号内标题能在本文件节标题集合中命中。
2. 每个二级节开头一句给出该节的可执行结论，随后才是展开。禁止以背景铺垫开篇。
3. 需顺序的规则改为编号步骤列表，禁止用顿号并列暗示顺序。
4. 每张判定表末行给出默认分支。若表格不适合承载默认分支，紧接表格写一句以「默认」开头的兜底规则。
5. 段落化长散文按语义拆为多个小节或编号条目。单条规则不超过 5 行。

## 3. 逐节契约

### §0 问题与解法

保持三条解法不变。末尾补一句指针：「本文后续各节的规则均须可被 Agent 直接执行，判据就近，权威单一。」

### §1 角色与交接

改「派发判定」为两问决策加单表。

第一问固定表述：「这个任务是只读的吗」。回答是则派 scout。

否则查表，表列仅两列。

| 产出物 | 承接者 |
|---|---|
| 需求文档 | ddd-requirements |
| 验收标准 | ddd-acceptance |
| 架构文档 | ddd-architect |
| 分解设计与 DESIGN 修订 | ddd-decomposer |
| 接口评审报告 | ddd-interface-reviewer |
| 代码与单元测试 | ddd-implementer |
| 测试计划 | ddd-test-planner |
| 测试报告与缺陷路由单 | ddd-tester |
| 缺陷修复与集成收口 | ddd-fixer |
| 仲裁裁决单 | ddd-arbiter |
| 文档巡检报告 | ddd-doc-sync |
| 审计报告 | ddd-auditor |
| 代码评审 | reviewer |
| 无匹配产出物 | 根会话直接完成 |

表后紧接三条禁令，取代原「不得承接者」列。

1. 只读任务不得派给任何具备写权限的 ddd-* 代理，即使任务看上去很小。
2. 承接者收到不符合自身职责的任务时停止并报告「派发类型不匹配」，注明缺失的前置输入，不得改换任务性质后推进。
3. 该拒绝导致该次子任务验收判 rejected，属预期信号而非代理异常，根会话据此改派或补足前置输入。

保留承接者合法拒绝的验收语义说明，保留 scout 与 reviewer 由 pi-subagents 随带且不加 ddd- 前缀的说明。

角色槽位表保留槽位号，但补一句：「槽位号为流程位置与排序标识，跨文档引用一律用代理名。代理名是唯一键。」

交接链保留，并在链上就地标注并行与串行，形如 `实现 ∥ 测试规划 → 集成收口 → 测试执行`，紧随其后一句：「测试执行与实现永不同段。」

### §2 质量门禁

门禁表新增首列「序」，取值 1 至 8，依次对应 G1、G2、G3、G4、G4.5、G5、G5-INT、G6。序列为流程推进的唯一顺序依据，门号列为标识。

退出条件拆为分号分隔的可勾选子项，每项自足可判定，不使用「齐备」「一致」等需再解释的概括词单独成项。

证据源列保持三类：脚本命令、指名代理、运行时守卫。三类须写明具体命令或代理名与判据。

元规则改写为两条，顺序固定。

1. 默认规则：本规范中可客观判定的条款均已挂门，门禁表即其归属索引。
2. 例外规则：仅下列条款未挂门，属指导性条款，不得作为验收依据。清单见本条下。

未挂门清单由实施者按可客观判定性逐一核出，至少覆盖 §0、§6 的并行前提段、§10、§14。发现某条本应强制却未挂门时，处理方式是补挂门，而非降为建议。

### §3 缺陷四级路由

保持四列表，列名不变：级别、定义、自检问题、处理。表末增加默认行说明：「未命中任一级特征时，默认取最低适用级别。」

表格之后以编号步骤写出自检流程，固定表述：

1. 自问该缺陷是否属 D 级。
2. D 级不成立时自问 C 级。
3. C 级不成立时自问 B 级。
4. B 级不成立时自问 A 级。
5. 命中即停，取该级处理动作。

保留「只有 B 级及以上回设计层」与「同一缺陷轮回修复超过 2 轮仍未解决，强制升级用户；仲裁计入轮回」。

### §4 粒度与独立性

阈值数字集中在本节，作为唯一权威定义处。固定表述锚点：「代码文件 500 行、基础或核心模块 300 行、文档 200 行或 10 项契约」。其他文档引用阈值时须与锚点一致，由 `ref-check` 校验。

「运行时例外」一条拆为四个独立判定项，依次为平台受限、文件头显式声明、单一能力域、未声明不适用。

### §5 接口先行与冻结

条款不变。引用改为语义化。G4.5 五项检查保持列举，并补一句：「五项任一不通过即判 fail。」

### §6 至 §10

条款内容不变，仅做三项改写：跨节引用语义化；长段拆条；§6 的并行前提段改为编号清单。§10 保持在未挂门清单内。

### §11 渐进式改造

入口条件前置为独立一段，置于表前，固定表述：「追加新功能时若现有设计不合理，或结构健康度量相对上次恶化，进入本节的改造分级。」

表格仅保留三列：级别、范围、处理。

「从最小级别起评」改为编号步骤，固定表述：

1. 从 L1 起评。
2. 范围超出该级时上移一级。
3. 命中即停，不得跳级命名。

「一次迭代只做一个级别」保留，并就地写出豁免关系：「本条约束 L2 及以上。见『结构与契约的演进治理』节的触碰即治理义务，属 L1，不受本条约束。」

### §12 声明面可验证与修剪

铁律保留。铁律之后紧接一条可勾选检查项，固定表述：「每条声明同时具备消费方与验证手段，缺一不得引入。」

写入者清理义务的范围表述保留，并在句末补一句指针：「义务的完整性见『结构与契约的演进治理』节的触碰即治理。」

审计停止条件与归档规则保留。归档建议名格式保留。

### §13 结构与注释的机械证据

五类事实表保留。新增一张脚本消费契约表，列为脚本、输出形态、机读结论、退出码、门禁地位、输出上限。填值与 `40-tooling.md` 的契约一致，是该表的唯一权威源。

表中各脚本的调用形式统一为 `node ~/.pi/agent/skills/ddd-methodology/scripts/<脚本名>.js <项目根>`。

保留 `health.json` 入版本管理与上限 50 条的说明。

### §14 本仓库适用边界

三条维护链保留，新增第四条：「改造设计文档位于 `docs/analysis/` 下的版本目录，是本仓库自我迭代的冻结契约来源。」

新增一段说明本仓库结构性改造的写入路径：「本仓库的结构性改造按改造设计文档执行，由根会话派发写入代理或由根会话直接实施，改完由文档巡检与声明面审计两条只读链收口。」

不适用清单保留，语义保持「报不适用而非缺口」。

### §15 状态文件

`doneStages` 的阶段键集合固定为：`requirements`、`acceptance`、`architect`、`decomposer`、`interface-review`、`implement-plan`、`g5-int`、`test-execute`、`audit`。

新增 `audit` 键以对齐 workflow 的九步。写入者规则保留，并补一句：「并行段仅实现者写。」

### §16 结构与契约的演进治理

拆为五个子节，标题为冻结值。

```
16.1 契约指纹
16.2 变更类型
16.3 触碰即治理
16.4 等价性验证
16.5 机械约束
```

16.1 保留算法唯一权威表述与指纹语义。16.2 保留重构三条件。16.3 保留治理义务与回执要求，回执句固定为「记录被触碰文件的改动前后规模、是否拆解与依据的粒度预判」。16.4 保留测试执行者的判定职责。

16.5 由整段散文改为结构如下。

1. 一段总述：可机械判定者分两层承载，声明式门禁为主，运行时守卫为辅。
2. 一张运行时守卫判定表，列为编号、触发点、判定条件、动作、当前覆盖。与 `extensions/ddd-governance.ts` 文件头逐项一致，由 `ref-check` 校验编号与触发点集合。
3. 一张阈值承载表，列为阈值、数值、承载体。写明哪一档由守卫硬拦、哪一档由脚本度量、哪一档由审计承接。
4. 一句守卫豁免：对非 DDD 项目静默，任何异常一律放行并记警告。

## 4. 冻结短语

下列短语本轮改造中固定，不得改写，其他文档引用时须逐字一致。

|---|---|

| 拒绝语义 | 派发类型不匹配 |

| 全量测试主体 | 全量测试的唯一主体是 ddd-tester |

## 5. 变更记录要求

本文件被触碰，按「结构与契约的演进治理」节填写变更记录。变更类型为行为变更，理由是本文件为规范而非 DESIGN，其修订不产生契约指纹，但改变 Agent 行为，须在 CHANGELOG 登记。
