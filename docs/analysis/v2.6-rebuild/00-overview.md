# v2.6 存量重建与定向重构设计总览

本轮新增两个由人工显式触发的场景，补齐方法论当前缺失的一整类需求，即存量重建。核心命题是让治理从「追加式修补」回归「改造式替换」，同时保证规范层绝对受约束、实现层充分开放。

## 1. 问题

现有体系无法表达丢弃重建，条款层面有三重排斥，均经只读调研确认。

| 排斥 | 条款 | 后果 |
|---|---|---|
| 禁止跨级 | 渐进式改造节规定一次迭代只做一个级别，从 L1 起评，命中即停 | 整体改造被制度性拆碎为多轮单级修补 |
| 禁止覆盖 | 需求变更节规定需求与 AC 版本化追加而非覆盖 | 设计文档只增不改，碎片累积 |
| 禁止重建 | 二次开发节规定新模块必须与原结构同构 | 结构性重生无路径 |

更深一层，结构与契约的演进治理节把「重构」定义为契约指纹不变，于是任何涉及契约的重建都被归类为行为变更，唯一出路是追加版本。这使「追加而非改造」成为条款下的理性选择。

此外，写入者的清理义务限于所触碰文件，仓库级遗留只由只读审计代理报告；报告不等于修复。这是碎片得以长期滞留的第二成因。

## 2. 新场景定位

两个 skill，均设 `disable-model-invocation: true`，模型不得自动选中，仅由用户以 `/skill:ddd-rebuild` 与 `/skill:ddd-refactor` 显式调用。触发时机由人工判断，落在入口。

| skill | 面向 | 触发信号 |
|---|---|---|
| ddd-rebuild | 全量重建。碎片累积到修补成本高于重建成本 | 用户判断项目已到需要重置的时点 |
| ddd-refactor | 定向重构。已知问题点或用户观点驱动的局部重构 | 用户指出具体模块或问题 |

两者复用既有 12 个代理，只新增编排与约束，不新增角色。

## 3. 开放与约束的分界

| 开放 | 绝对约束 |
|---|---|
| 架构方案、目录划分、技术选型、实现路径、拆分粒度、内部命名 | 产物形态与字段、流程顺序与门禁、锚点继承、废弃声明、等价性验证、回溯点记录、变更记录 |

开放区的含义是重构者可自由选择最优形态，不受旧实现的任何结构牵制。约束区的含义是无论方案如何选，产物与流程都必须按本节契约产出，不得自创格式或跳过门禁。

## 4. 版本控制前提

「丢弃」是相对旧版本的丢弃，不是绝对丢失。旧版本必须始终可回溯。

因此重建的前置条件为一硬约束，见 `10-spec.md`。要点是确认版本控制系统在场、记录回溯点标识、并在重建产物中持久化该标识。重建期间需要参照旧实现时，从回溯点读取而非保留旧文件在案。

## 5. 从发散到收敛

重建流程在时间上分为两段，中间由一道人工门分隔。

| 段 | 性质 | 动作 |
|---|---|---|
| 发散段 | 探索 | 现状全量盘点、问题诊断、锚点候选、方案候选。允许广泛试错，产物为草稿，不入基线 |
| 锚点冻结门 | 用户确认 | 冻结价值锚点与重建范围。冻结后不得再扩范围 |
| 收敛段 | 执行 | 按冻结锚点生成新设计、实施、验证、审计。严格按模板产出，不得夹带范围外变更 |

发散段的产物在冻结后即作废，只有冻结后的产物进入正式文档树。

## 6. 持续收敛的机制化

引入架构基线。架构文档即当前架构最佳形态的声明，每次重建后整体重写。

后续每次迭代的审计须核验实现与基线的偏离，偏离须给出理由或登记为存量债务。这样「持续收敛至当前架构最佳」有可判定的落点。

## 8. 验收标准

| 编号 | 验收要点 | 判定方式 |
|---|---|---|
| AC-1 | 两个 skill 均不可被模型自动选中，仅显式命令可用 | 检查 frontmatter 与加载行为 |
| AC-2 | 重建前置检查覆盖版本控制在场与工作区状态，缺失即停止 | 契约核对加人工核查 |
| AC-3 | 回溯点标识在重建产物中持久化 | 模板字段核对 |
| AC-4 | 锚点冻结门不可跳过，未确认不得进入收敛段 | 流程与门禁核对 |
| AC-5 | 旧产物废弃声明完整，无静默保留 | 模板与审计核对 |
| AC-6 | 重建的行为等价性以 AC 全量回归验证 | 规范条款核对 |
| AC-7 | skill 清单在仓库与安装脚本间一致 | 机械校验 |
| AC-8 | 既有流程与门禁未被削弱 | 全量校验回归 |

## 10. 版本

本轮定为 v2.6.0。属新增能力，对既有流程无破坏性变更，既有门禁与证据源不变。新增 skill 由 `disable-model-invocation` 隔离，不影响日常自动路由。
