本文件承载「本仓库适用边界」「状态文件」「结构与契约的演进治理」三节；不包含面向应用项目的门禁、变更与重建条款。

## 15. 本仓库适用边界

项目门禁与交付条款面向**被开发的应用项目**；本方法论仓库自身是规范与工具，不含应用代码，其维护只走四条链：

| 适用 | 链路 |
|---|---|
| 文档一致性 | ddd-doc-sync 巡检 |
| 声明面与结构健康 | ddd-auditor 审计，证据源为 code-health |
| 结构治理 | 触碰即治理与存量的粒度、清理、重复治理，证据源为 code-health 与运行时守卫，见「结构与契约的演进治理」节 |
| 术语表维护 | 根会话在迭代收尾核验更新，其条目时效性判据同项目级指令文件 |
| 改造设计文档 | 位于本仓库内部档案区（见公开索引 `docs/README.md`），是本仓库自我迭代的冻结契约来源，属内部档案，不随公开仓库发布；历史改造与重建设计记录归档于同一内部档案区 |

本仓库的结构性改造按改造设计文档执行，由根会话派发写入代理或由根会话直接实施，改完由文档巡检与声明面审计两条只读链收口。

本仓库自身的审计记录归档于内部档案区（见公开索引 `docs/README.md`），属内部档案，不随公开仓库发布；被开发项目的审计归档位置仍为 `<项目根>/docs/audits/`，两侧边界不得混用。

契约指纹以 DESIGN 为对象，本仓库无 docs/design，故报不适用而非缺口。

不适用：G1、G2、G3、G4、G4.5、G5 的证据源，无论脚本或指名代理。原因是本仓库无 REQUIREMENTS.md、AC.md、ARCHITECTURE.md 与 docs/design，这些门无对象可判；审计中报为不适用而非缺口。trace-check 同样因无 AC.md 在本仓库零可运行范围。

存量重建节面向被开发的应用项目，本仓库自身不适用，理由同本节其余各门。

## 16. 状态文件

workflow 加速档以 `<项目根>/docs/.ddd-state.json` 记录进度。

```json
{ "doneStages": ["requirements", "architect"], "lastStage": "architect", "status": "done" }
```

`doneStages` 的阶段键集合与 workflow 的阶段流一一对应：requirements、acceptance、architect、decomposer、interface-review、implement-plan、g5-int、test-execute、audit。`audit` 键由审计阶段写入，用于对齐 workflow 的阶段流。

每个阶段完成后由该阶段代理或其后继写入者合并更新。并行段仅实现者写。JSON 损坏时中断续跑并交根会话，不得当作全新启动。

## 17. 结构与契约的演进治理

### 17.1 契约指纹

DESIGN 的契约表内容取哈希作指纹，版本号由指纹前八位派生。算法唯一权威在本条：

1. 取 DESIGN 中标题为「对外接口与约定」的一节，自该标题起至下一个二级标题前的内容。
2. 剔除其中的契约指纹行本身。
3. 逐行去首尾空白后以换行连接，去尾部空行。
4. 取 SHA-256 十六进制前八位。

指纹是冻结的锚点，回答「冻结的是哪一版」。指纹未变即结构可自由改动，无需审批，但仍须遵守粒度预判与触碰即治理义务，无需审批不等于无需设计预判；指纹变化即行为变更，必须递增版本并走 B 级路由同步 AC，不得静默修改。指纹的机械校验由 trace-check 承担，门槛校验由 governance-check 承担。

### 17.2 变更类型

每次改动须声明类型。重构为契约指纹不变、行为用例全绿、结构度量改善三者同时成立；行为变更为契约指纹变化。重建为整体替换既有实现与文档，属行为变更的特例，须附废弃清单与回溯点，等价性以 AC 全量回归验证。声明类型与实际证据不符即为缺陷。

### 17.3 触碰即治理

写入者对所触碰文件的存量结构负治理义务，不限于清理连续注释代码与兼容层标记，代码与文档同等适用，判据为「粒度与独立性」节的粒度阈值。

文件已达或接近阈值时先按就近 DESIGN 的粒度预判拆解，无法拆解方上报。拆解不得超出 DESIGN 预判，超出属设计偏离走 B 级。

全部写入代理的完成报告均须附结构治理回执，记录被触碰文件的改动前后规模、是否拆解与依据的粒度预判；其中代码写入者记改动前后行数与是否拆解，文档写入者记产出文档规模与「粒度与独立性」节文档粒度阈值的比对。空节不得声明完成。本义务属 L1，不受「渐进式改造」节一轮一级约束。

### 17.4 等价性验证

测试执行者先判定变更性质。指纹不变时验证用例集合未减少且全绿；指纹变化时核对版本已递增与 AC 已同步，未同步报 B 级。测试用例集合逆向缩减是堆叠信号。

### 17.5 机械约束

可机械判定者分两层承载：声明式门禁为主，运行时守卫为辅。

声明式门禁为代理 frontmatter 的 acceptanceRole、acceptance 与派发 options 的 gate，对所有子代理生效；写入类与审计类代理已显式声明，其余代理沿用 pi-subagents 的默认推断，属分级而非遗漏。写入类代理显式关闭 acceptanceRole 带来的自动评审推断，独立评审由 G4.5 与 G6 承担，避免每次实现重复评审。

运行时守卫由 `extensions/ddd-governance.ts` 在工具调用处拦截。

**守卫覆盖面**。默认覆盖根会话与后台子代理。前台子代理不加载环境扩展，因此产出源码或测试代码的写入类代理在其 frontmatter 显式声明 `extensions: ../extensions/ddd-governance.ts`，当前为 ddd-implementer、ddd-fixer 与 ddd-tester 三份；新增写代码代理时须同步声明并在此登记，未登记者视为不受写入强制覆盖。

**看板注入**。`extensions/ddd-governance.ts` 在每次代理启动时读取 `docs/board/` 下的模块节点文件，把未开始与进行中的义务节点注入系统提示的一个 section；任务树未启用或未闭合节点为空时不注入。

| 编号 | 触发点 | 判定条件 | 动作 | 当前覆盖 |
|---|---|---|---|---|
| H-1 | tool_call 的 write/edit | 估算写入后行数超 500 行 | 拦截，理由含文件路径、就近 DESIGN 路径与拆解要求 | 代码文件 500 行阈值；文件内显式声明运行时例外者放行 |
| H-2 | tool_call 的 bash | 命令属窄口径的全量测试调用形态，且 `docs/.ddd-state.json` 的 lastStage 为 `g5-int` | 拦截，指明全量测试的唯一主体是 ddd-tester | 整仓测试命令的窄口径写法 |
| H-3 | tool_call 的 write/edit | 目标为源码文件、任务树已启用，而该文件所属接缝的节点文件缺失或该文件未被任何义务节点覆盖 | 拦截，理由含节点文件路径与登记方式 | 任务树已启用的项目；设计树根取 ARCHITECTURE 的声明值，缺省回退 docs/design；源目录内 DESIGN 组织不在覆盖内 |
| H-4 | tool_call 的 write/edit | 目标为 `docs/gates/` 下的门禁记录，且任务树存在未闭合义务节点 | 拦截，理由含未闭合节点所在文件与逐项核销要求 | 任务树已启用的项目；未启用时放行 |

默认：未命中 H-1 至 H-4 的工具调用一律放行。

阈值按档位分配承载：

| 阈值 | 数值 | 承载体 |
|---|---|---|
| 代码文件 | 500 行 | 运行时守卫硬拦（H-1） |
| 基础或核心模块 | 300 行 | `code-health.js` 脚本度量 |
| 文档 | 200 行 | `code-health.js` 文档规模度量，并配 ddd-decomposer 拆解判定与 ddd-auditor 抽检 |
| 文档契约数 | 10 项 | `code-health.js` 文档规模度量，并配 ddd-decomposer 拆解判定与 ddd-auditor 抽检 |

命令级门禁由 `governance-check.js` 承担，命令路径可确定时经 typed gate 挂载，不可用 permission 实现，因其对 bash 恒放行。

守卫豁免：对非 DDD 项目静默，任何异常一律放行并记警告。

### 17.6 项目级指令文件的维护

项目级指令文件指置于项目根的 `AGENTS.md`，按模板的五节骨架产出，由运行时逐字注入各子代理的常驻上下文，直接决定子代理看到的项目约定。本仓库自身不落该文件，其维护面向被开发的应用项目。

维护责任与触发，每个触发点均有对应承接方。初版在架构设计期产出，由 ddd-architect 负责：

| 触发点 | 承接方 |
|---|---|
| 能力新增后 | 架构设计期产出或更新 |
| 目录或依赖方向变更后 | 架构设计期产出或更新 |
| 约定变更后 | 架构设计期产出或更新 |
| 结构健康恶化时 | 纳入审计 |
| 迭代收尾 | 根会话核验并做适应性更新 |

不由各写入者各自追加，避免其退化为追加式堆积。

本表的触发点与承接方同时适用于项目根的 `GLOSSARY.md`，其条目时效性核验与内容边界判据同本节上文的维护责任段与内容边界段。

内容边界，写五类，均为项目特有或当前生效者：

1. 项目定位与技术栈。
2. 目录结构与依赖方向。
3. 本项目特有约定与禁忌，逐条带判据。
4. 本项目实际使用的方法论要点，含门禁与产物路径。该类目承载现行机制形态，即机械校验经 `ddd_*` 工具运行并区分 G5 与 G5-INT 的证据产出方，模型配比经 `/ddd-models` 应用与撤回、解析器按需经 `/ddd-parser-install` 安装，判定对象不存在时报「不适用」而非缺口。
5. 已知债务与遗留，含接受理由或承接去向。

不写方法论的通用条款。理由是该文件会被复制到每个项目，复制方法论全文会形成副本，与本方法论「单一权威与就近送达」的原则冲突；项目实际使用的部分以要点内联，通用部分保持在方法论本体。

适应性重构的判据：局部过时做适应性修订，不整篇重写；满足下列任一条时整篇重写。

1. 超过文档粒度阈值，即 200 行。
2. 出现描述与实际不符的条目。
3. 出现无消费方的条目，即项目已不再使用该约定或能力。

这三条与「声明面可验证与修剪」节、「粒度与独立性」节和「存量重建」节的判据同源，保持全仓判据一致。

与既有机制的边界，四层不互相替代：

| 机制 | 层级 | 作用 |
|---|---|---|
| 全局规则 | 用户级 | 跨项目强制规则 |
| 方法论规范 | 方法论级 | 跨项目通用条款 |
| 项目级指令文件 | 项目级 | 本项目特有约定与方法论要点 |
| 派发任务文本 | 任务级 | 单次派发的判据内联 |

项目的关键规则若子代理必须看到，写入项目级指令文件或派发任务文本，不得只留在方法论本体。
