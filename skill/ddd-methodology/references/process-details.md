# 方法论专项细则（B/C/D/E/F 主题）

> **主从契约**：本文件仅展开 spec.md §7 索引表中标注的专项细则，不引入 spec.md 未提及的新规则；冲突时以 spec.md 为准。变更历史见仓库 CHANGELOG.md。

## B. 多模块并行实现策略（代理4 调度规范）

### 接缝划分（Seam 划分）
1. 根会话在派发实现前，依据 `docs/design/` 文档树的依赖约束图，将实现工作划分为**互斥接缝**：每个接缝 = 一个目录或一组强内聚目录，接缝之间无文件交集。
2. **一个接缝一个 writer**：同一目录/同一文件在任一时刻只允许一个实现者代理持有写权限，禁止并行 writer 越界修改他人接缝内的文件。
3. 接缝间只通过 DESIGN.md 声明的"对外接口/约定"耦合；发现需要修改他人接口时，停止并报告（B 级设计问题走路由），不得自行改动。

### 并行派发条件
仅当同时满足以下条件才并行派发：
- 接缝已按依赖约束图分层，无循环依赖；
- 各接缝的 DESIGN.md、模块级 AC、TEST_PLAN 均已就绪（质量门禁通过，见 E）；
- 横切规范已在 ARCHITECTURE.md 集中定义，无需各 writer 自行协商。

### 隔离与集成
- 默认同仓库并行（各自持互斥目录），根会话在全部 writer 完成后统一收口集成。
- 接缝改动面大、或需要实验性改动时，使用 `worktree: true` 隔离 lane；使用前必须保证源检出干净。
- 集成收口后由根会话触发代理6 做一轮集成测试。

## C. 需求变更流程（A 级路由正式化）

开发中途用户变更需求时，按以下流程处理：

1. **变更受理**：用户变更 → 根会话登记变更单（变更编号、内容、提出时间）。
2. **版本化**：代理1 修订 `REQUIREMENTS.md` → 代理0 修订 `AC.md`。两文件必须携带变更记录表（版本号、变更编号、变更内容、影响范围），不覆盖历史，只追加。
3. **影响圈定**：代理3 依据"模块级 AC ↔ 总 AC 双向追溯"，圈定受影响的 `DESIGN.md` 集合（受影响模块级 AC 的模块），输出影响清单：需重设计的目录 / 不受影响的目录。
4. **重设计**：仅对受影响目录派发代理3 重设计 → 代理5 修订对应 TEST_PLAN → 代理4 重实现受影响接缝（按 B 规则可并行）。
5. **回归**：代理6 执行受影响模块回归测试 + 一次全量集成测试。
6. 全程遵守缺陷四级路由与 2 轮终止约束。

## D. 二次开发细则强化（代理2 执行标准）

### 现状分析报告标准格式（仅限缺少规范文档的二次开发项目）
```markdown
# 现状分析报告
## 1. 项目概况（技术栈、构建方式、入口、部署形态）
## 2. 现有目录结构与职责推断（逐目录一句话）
## 3. 原有准则提炼
- 命名/风格准则（来源：现有代码归纳 / lint 配置 / README / contributing）
- 依赖管理准则
- 测试组织方式
- 日志与异常处理惯例
## 4. 同构约束清单（新增模块必须遵守的条目，逐条可检查）
## 5. 风险与坑位（遗留问题、脆弱点）
```

### "对齐原准则"检查清单（代理2 设计前逐条核对）
- [ ] 新目录编排与现有结构同构
- [ ] 命名风格与现有代码一致
- [ ] 依赖方向不引入反向依赖
- [ ] 构建配置变更最小化
- [ ] 不破坏现有测试的组织方式

## E. 质量门禁（阶段门）

每个阶段的交付物必须通过退出条件才能进入下一阶段；根会话负责把关，未过门禁一律退回上一代理。

| 阶段门 | 进入条件（交付物齐备） | 退出条件（放行标准） |
|---|---|---|
| G1 需求→验收 | REQUIREMENTS.md 无"待确认"项 | 需求对齐声明存在；代理0 无需求矛盾报告 |
| G2 验收→架构 | AC.md 覆盖全部需求、双向可追溯 | AC 条目均可客观判定 |
| G3 架构→分解设计 | ARCHITECTURE.md 齐备（环境/目录/横切规范/**设计文档树根路径声明**；二次开发含现状分析报告+检查清单通过） | 目录树完整、每目录有职责、文档树根路径已声明 |
| G4 分解设计→实现/测试规划 | 文档树覆盖全部实现目录 | 模块级 AC 之和覆盖总 AC；无悬空接口引用 |
| G5 实现/测试规划→测试执行 | 代码+单测完成且自测通过；TEST_PLAN 覆盖全部模块级 AC | 计划与代码均已就绪 |
| G6 测试→交付 | 测试通过率 100%，或未通过项已定级路由且轮回未超限 | 根会话按总 AC 终验 |

## G4.5 接口冻结门（G4→G5 之间）

接口先行规划：分解设计完成后、实现启动前，对模块对外接口做签名级定稿与交叉审查：
1. **签名级契约**：代理3 将各模块 DESIGN.md 的"对外接口/约定"升格为签名级（签名/参数/返回/错误语义/调用示例）。
2. **独立评审**：派发 ddd-interface-reviewer（只读）交叉审查：能力覆盖/模块间重复/缺口/依赖方向/契约质量，输出缺陷清单与结论。
3. **根会话复核**：审查无"必须修复项"（或有条件通过且修复完成）后，根会话确认冻结。
4. **冻结效力**：接口一经冻结即为硬约束——实现逐字匹配签名；测试规划者可直接基于冻结接口产出契约测试；修改接口 = B 级设计变更走正式路由（不可静默改）。
5. 加速档 workflow 对应状态键 `interface-frozen`；接口评审发现的缺陷按严重度路由（接口设计问题 → B 级回代理3）。

**并行实现的门禁特例（配合 B）**：各接缝 writer 需通过 G5 的各自子门（该接缝代码自测通过）才允许收口集成；集成门（G5-INT）要求集成后构建与全量单测通过，**workflow 加速档在并行段后同样插入 G5-INT 集成收口检查，两档标准一致**。

**门禁检查单**：根会话过门时按模板填写并写入 `<项目根>/docs/gates/Gx-记录.md`（每道门一组 checkbox + 证据路径 + 结论）；G2/G4/G5 必须附 trace-check.js 运行输出作为证据（模板见 templates.md）。

## F. 测试阻塞防护（实战经验沉淀）

背景：实现者与测试者在同一代理进程内切换运行时，个别长时间运行的测试任务（死循环、等待外部资源、性能压测等）会彻底卡住代理进程，导致整条方法论链路中断。

### 测试任务分级与准入规则（代理5 制定计划时执行）
1. 计划中每个用例必须标注**预估运行时长**与**风险级别**：
   - **常规用例**：预期秒级完成，可直接自动执行；
   - **高风险用例**：涉及网络 IO、长循环、大数据量、外部服务、真实等待（sleep/超时重试）的用例。
2. **高风险用例默认禁止直接自动执行**，必须先改写为以下两种方式之一：
   - **桩模块替代**：以 stub/mock/fake 替换外部依赖与耗时环节（如网络客户端、文件系统、时钟、随机源），使测试在毫秒级完成且断言点不变；
   - **隔离降级**：无法桩化的用例移入"手动测试清单"，不进入自动执行集。
3. 计划文档的 TEST_PLAN.md 需新增一节"手动测试清单"，逐条列出：用例ID、无法自动化的原因、手动操作步骤、预期结果。

### 超时控制（代理6 执行测试时执行）
1. 代理6 执行测试命令时必须带超时限制（如 `timeout` 命令或测试框架的 per-test timeout），单用例超时上限建议 60 秒，全量套件上限建议 10 分钟。
2. 用例超时即视为**失败**并记录：按 D 级（未桩化的高风险用例漏入自动集 → 代理5 补桩或移入手动清单）或 C 级（实现死循环/资源未释放 → 代理4 修码）定级路由。
3. **禁止**代理6 在无超时保护下重跑已知长耗时用例；连续 2 次超时后该用例强制移入手动测试清单，不再自动重试。

### 手动测试反馈闭环
1. 手动清单中的用例由**用户手动执行并反馈结果**（通过/失败/现象描述），根会话负责转交与登记。
2. 反馈失败的手动用例：由代理6 按四级路由正常定级处理。
3. 全量测试报告需区分"自动通过/自动失败/手动待反馈/手动失败"四类，手动待反馈项不阻塞其余缺陷的路由与修复。

### G5 阶段门补充条件
- TEST_PLAN.md 含"预估时长/风险级别"标注与"手动测试清单"，且高风险用例均已桩化或降级，方可过门。
