## B. 多模块并行实现策略，代理4 调度规范

### 接缝划分

接缝划分即 Seam 划分。

1. 根会话在派发实现前，依据 `docs/design/` 文档树的依赖约束图，将实现工作划分为**互斥接缝**：每个接缝 = 一个目录或一组强内聚目录，接缝之间无文件交集。
2. **一个接缝一个 writer**：同一目录/同一文件在任一时刻只允许一个实现者代理持有写权限，禁止并行 writer 越界修改他人接缝内的文件。
3. 接缝间只通过 DESIGN.md 声明的"对外接口/约定"耦合；发现需要修改他人接口时，停止并报告，B 级设计问题走路由，不得自行改动。

### 并行派发条件

仅当同时满足以下条件才并行派发：
- 接缝已按依赖约束图分层，无循环依赖；
- 各接缝的 DESIGN.md、模块级 AC、TEST_PLAN 均已就绪，质量门禁通过，见 E；
- 横切规范已在 ARCHITECTURE.md 集中定义，无需各 writer 自行协商。

### 隔离与集成
- 默认同仓库并行，各自持互斥目录，根会话在全部 writer 完成后统一收口集成。
- 接缝改动面大、或需要实验性改动时，使用 `worktree: true` 隔离 lane；使用前必须保证源检出干净。
- 集成收口后由根会话触发代理6 做一轮集成测试。

## C. 需求变更流程，A 级路由正式化

开发中途用户变更需求时，按以下流程处理：

1. **变更受理**：用户变更 → 根会话登记变更单，记录变更编号、内容、提出时间。
2. **版本化**：代理1 修订 `REQUIREMENTS.md` → 代理0 修订 `AC.md`。两文件必须携带变更记录表，包含版本号、变更编号、变更内容、影响范围，不覆盖历史，只追加。
3. **影响圈定**：代理3 依据"模块级 AC ↔ 总 AC 双向追溯"，圈定受影响的 `DESIGN.md` 集合，即受影响模块级 AC 所在的模块，输出影响清单：需重设计的目录 / 不受影响的目录。
4. **重设计**：仅对受影响目录派发代理3 重设计 → 代理5 修订对应 TEST_PLAN → 代理4 重实现受影响接缝，按 B 规则可并行。
5. **回归**：代理6 执行受影响模块回归测试 + 一次全量集成测试。
6. 全程遵守缺陷四级路由与 2 轮终止约束。

## E. 质量门禁，阶段门

每个阶段的交付物必须通过退出条件才能进入下一阶段；根会话负责把关，未过门禁一律退回上一代理。

| 阶段门 | 进入条件，即交付物齐备 | 退出条件，即放行标准 |
|---|---|---|
| G1 需求→验收 | REQUIREMENTS.md 无"待确认"项，即交付物齐备 | 需求对齐声明存在；代理0 无需求矛盾报告，即放行标准 |
| G2 验收→架构 | AC.md 覆盖全部需求、双向可追溯 | AC 条目均可客观判定 |
| G3 架构→分解设计 | ARCHITECTURE.md 齐备，含环境、目录、横切规范、**改造影响评估**与**设计文档树根路径声明**；二次开发含现状分析报告且检查清单通过 | 目录树完整、每目录有职责、文档树根路径已声明、改造评估表齐备 |
| G4 分解设计→实现/测试规划 | 文档树覆盖全部实现目录 | 模块级 AC 之和覆盖总 AC；无悬空接口引用 |
| G5 实现/测试规划→测试执行 | 代码+单测完成且自测通过；TEST_PLAN 覆盖全部模块级 AC | 计划与代码均已就绪 |
| G6 测试→交付 | 测试通过率 100%，或未通过项已定级路由且轮回未超限 | 根会话按总 AC 终验 |

## G4.5 接口冻结门

位置在 G4→G5 之间。接口先行规划：分解设计完成后、实现启动前，对模块对外接口做签名级定稿与交叉审查：
1. **签名级契约**：代理3 将各模块 DESIGN.md 的"对外接口/约定"升格为签名级，包含签名、参数、返回、错误语义与调用示例。
2. **独立评审**：派发只读的 ddd-interface-reviewer 交叉审查：能力覆盖/模块间重复/缺口/依赖方向/契约质量，输出缺陷清单与结论。
3. **根会话复核**：审查无"必须修复项"，或有条件通过且修复完成后，根会话确认冻结。
4. **冻结效力**：接口一经冻结即为硬约束——实现逐字匹配签名；测试规划者可直接基于冻结接口产出契约测试；修改接口 = B 级设计变更走正式路由，不可静默改。
5. 加速档 workflow 对应状态键 `interface-review`，与脚本 stages 键一致；接口评审发现的缺陷按严重度路由，接口设计问题 → B 级回代理3，已登记于 defect-routing.md 路由矩阵。

**并行实现的门禁特例，配合 B 规则**：各接缝 writer 需通过 G5 的各自子门，即该接缝代码自测通过，才允许收口集成。集成门 G5-INT 要求构建通过、各接缝自测报告齐备并声明测试就绪；**门禁任务禁止包含全量测试执行，全量测试的唯一主体是代理6 首轮执行，其结果作为 G5-INT 的最终证据，workflow 加速档在并行段后同样插入 G5-INT 集成收口检查，两档标准一致**。

**门禁检查单**：根会话过门时按模板填写并写入 `<项目根>/docs/gates/Gx-记录.md`，每道门一组 checkbox 加证据路径与结论；G2/G4/G5 必须附 trace-check.js 运行输出作为证据，模板见 templates.md。

## F. 测试阻塞防护，实战经验沉淀

背景：实现者与测试者在同一代理进程内切换运行时，个别长时间运行的测试任务，如死循环、等待外部资源、性能压测等，会彻底卡住代理进程，导致整条方法论链路中断。

### 测试任务分级与准入规则

代理5 制定计划时执行。
1. 计划中每个用例必须标注**预估运行时长**与**风险级别**：
   - **常规用例**：预期秒级完成，可直接自动执行；
   - **高风险用例**：涉及网络 IO、长循环、大数据量、外部服务、真实等待，如 sleep 或超时重试的用例。
2. **高风险用例默认禁止直接自动执行**，必须先改写为以下两种方式之一：
   - **桩模块替代**：以 stub/mock/fake 替换外部依赖与耗时环节，如网络客户端、文件系统、时钟、随机源，使测试在毫秒级完成且断言点不变；
   - **隔离降级**：无法桩化的用例移入"手动测试清单"，不进入自动执行集。
3. 计划文档的 TEST_PLAN.md 需新增一节"手动测试清单"，逐条列出：用例ID、无法自动化的原因、手动操作步骤、预期结果。

### 超时控制

代理6 执行测试时执行。

1. 代理6 执行测试命令时必须带超时限制，如 `timeout` 命令或测试框架的 per-test timeout；单用例超时上限建议 60 秒，全量套件上限建议 10 分钟。
2. 用例超时即视为**失败**并记录：未桩化的高风险用例漏入自动集 → 按 D 级路由，代理5 补桩或移入手动清单；实现死循环或资源未释放 → 按 C 级路由，代理4 修码。
3. **禁止**代理6 在无超时保护下重跑已知长耗时用例；连续 2 次超时后该用例强制移入手动测试清单，不再自动重试。

### 手动测试反馈闭环

1. 手动清单中的用例由**用户手动执行并反馈结果**，反馈内容为通过、失败或现象描述，根会话负责转交与登记。
2. 反馈失败的手动用例：由代理6 按四级路由正常定级处理。
3. 全量测试报告需区分自动通过、自动失败、手动待反馈、手动失败四类，手动待反馈项不阻塞其余缺陷的路由与修复。

### G5 阶段门补充条件

- TEST_PLAN.md 含"预估时长/风险级别"标注与"手动测试清单"，且高风险用例均已桩化或降级，方可过门。

## H. Workflow 状态文件 schema

本节是加速档断点续跑契约。

状态文件路径：`<项目根>/docs/.ddd-state.json`；唯一权威定义在本节，SKILL.md 与 workflow 注释只留指针。

```json
{
  "doneStages": ["requirements", "acceptance", "architect", "decomposer", "interface-review", "implement-plan", "g5-int", "test-execute"],
  "lastStage": "interface-review",
  "status": "done",
  "fixRounds": 0,
  "lastGate": "G4.5"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| doneStages | string[] | 已完成阶段键，取值必须来自阶段注册表：requirements / acceptance / architect / decomposer / interface-review / implement-plan / g5-int / test-execute |
| lastStage | string | 最近完成的阶段键 |
| status | string | "done" / "in-progress" / "escalated" |
| fixRounds | number | 当前缺陷修复轮次，可选 |
| lastGate | string | 最近一道已过门记录，可选，如 "G4.5"、"G5-INT" |

**写入规则**：每个阶段完成后由该阶段代理追加或合并，并行段仅实现者写，writer 唯一；JSON 损坏时 resume-check 输出 `STATE_CORRUPT` 拦截，不得当全新启动。

## I. 设计粒度规则

本节分两部分：文档粒度，规定大体量同构场景的 DESIGN.md 拆解；代码粒度，规定基础代码与能力的文件拆解及独立单元测试。背景：单一 DESIGN.md 承载大量同规格业务场景，如多个同构命令、多种导出格式，时，文档体量膨胀导致就近加载效率下降、上下文负担回升，与本方法论核心目标冲突。

### 拆解判定标准

满足其一即拆，代理3 在分解设计时判定。

1. **同构场景数 ≥ 3**：签名同构或行为模式重复的业务场景，如 add/list/done/rm 四个命令；
2. **单一 DESIGN.md 体量上限**：超过约 200 行，或接口契约超过 10 项。

### 拆解形态

代理3 按内聚性自选。**形态一：分类文件**，适用于场景数少、单场景契约简单的情形。
```
docs/design/src/commands/
├── DESIGN.md          # 共性约定（统一签名、公共错误语义）
├── DESIGN.add.md      # add 场景差异契约
├── DESIGN.list.md     # ...
```
**形态二：内部子目录**，适用于场景数多或单场景自身复杂的情形。
```
docs/design/src/commands/
├── DESIGN.md          # 目录级：共性契约 + 子场景索引表
└── add/DESIGN.md      # 场景级：差异契约 + 场景级 AC
└── list/DESIGN.md
```

### 配套硬规则
1. **父级不重复**：父级 DESIGN.md 只保留"共性契约 + 子场景索引表"，索引表结构为子场景→文件路径→一句话职责，禁止复述子场景细节；子 DESIGN.md 只写差异与场景级 AC。
2. **代码镜像**：文档树拆解形态必须与代码实现结构同构，如 commands/add.js 或 commands/add/，实现者按文档树镜像落位。
3. **场景级 AC**：总 AC 拆分时允许跨两级，即从目录级到场景级，trace-check 递归扫描天然兼容。
4. **G4.5 评审增项**：接口评审者须检查拆解均匀性——父级不得残留子场景细节，防止巨石空壳反模式。
5. **需求变更影响圈定**：变更影响以最小粒度圈定，即目录级到场景级，减少重设计范围。

### 代码粒度规则

设计阶段对代码文件体量做预判性拆解，防止问题被隐藏后在集成测试中集中暴露。

**拆解判定标准，设计期由代理3 对照 ARCHITECTURE.md 的基础能力清单判定，满足其一即拆。**

1. 单文件行数超过 500 行，基础或核心模块从严按 300 行评估；
2. 单文件承载 2 个及以上独立可测能力；
3. 被多个模块依赖的基础能力，如存储、序列化、校验器、工具函数，必须独立成文件。

**分组拆解原则。**

1. 基础能力按能力域分组，例如存储读写、ID 分配、损坏检测各自成文件；
2. 拆出文件在 DESIGN.md 有独立契约条目与场景级验收要点；
3. **独立单元测试强制**：拆出的基础能力文件必须有同名对应测试文件且用例独立可跑，问题在最内层暴露，不外溢到集成测试；
4. 实现者禁止在实现时合并已拆解的文件。

**流程落点。**

1. 代理2 在 ARCHITECTURE.md 维护"基础能力清单"，列明基础能力、所属文件与对应测试文件，代理3 据此拆解；
2. 代理3 在 DESIGN.md 中预判实现文件粒度，标注每个实现文件的职责边界；
3. G4.5 接口评审者增加检查项：实现文件粒度规划是否合理，是否存在应拆未拆的大文件预判；
4. 代理5 在 TEST_PLAN 中为基础能力文件的独立用例单独列节；
5. 代理6 执行时优先运行基础能力独立用例，先内层后外层，失败即定位到最小能力域。

## J. 渐进式改造

原则：追加新功能时若现有设计不合理，可对现有设计进行改造；改造遵循**迭代版本、逐步完成**，改造级别从最小影响范围开始评估，低级别能解决的不升级。

### 改造级别阶梯
| 级别 | 影响范围 | 典型场景 | 评估/执行主体 |
|---|---|---|---|
| L1 文件级 | 单文件内 | 函数重命名、内部结构调整 | 实现者自行完成，写入 DESIGN.md 变更记录 |
| L2 目录级 | 单目录内多文件 | 模块内文件重组、粒度拆解调整 | 代理3 修订 DESIGN.md，实现者执行 |
| L3 模块级 | 跨目录、契约变更 | 冻结接口修改、能力边界调整 | **B 级设计变更走正式路由**，代理2/3 修订 |
| L4 架构级 | 目录树、依赖方向 | 新增顶层目录、依赖约束变化 | 根会话确认后代理2 修订 ARCHITECTURE.md |
| L5 项目级 | 技术环境、全局规范 | 换构建工具、横切规范重定义 | **必须升级用户确认** |

### 评估时机
- **代理2 在架构设计时执行改造影响评估**：对照 L1–L5 评估现有设计对新功能的适配性，产出改造评估表（新功能 → 改造级别 → 改造内容 → 是否涉及冻结接口）。
- 评估结果写入 ARCHITECTURE.md 的「改造影响评估」章节，是 **G3 门退出条件**之一。
- L3 及以上：改造内容随设计修订同步进入接口契约；L4/L5：根会话/用户确认后才出架构方案。

### 执行约束
1. 改造逐步完成：一次迭代只做一个级别的事，禁止跨级合并改造。
2. 每级改造完成后运行对应验证（L1/L2 自测、L3 重跑契约测试、L4/L5 全量回归）。
3. 改造说明必须写入 DESIGN.md 变更记录，跨级改造需登记到 CHANGELOG 层面的项目记录。
