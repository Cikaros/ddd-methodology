# 分治式设计驱动方法论规范

## 0. 问题与解法

单一巨型设计文档使子代理上下文过载，实现随之偏离设计。

解法三条：**文档随架构分治**，每个有实现内容的目录一份 DESIGN；**上下文随职责分治**，代理只加载本阶段所需；**缺陷随层级路由**，小问题就地修，只有设计级及以上才回设计层。

本文后续各节的规则均须可被 Agent 直接执行，判据就近，权威单一。

## 1. 角色与交接

派发前先回答一个问题，答否再查表；角色只由代理名标识，槽位号仅作排序。

| 槽位 | 代理 | 职责 | 产出 |
|---|---|---|---|
| 1 | ddd-requirements | 细化需求，与用户确认对齐，判定新建或二次开发 | REQUIREMENTS.md |
| 2 | ddd-acceptance | 需求转可执行验收标准 | AC.md |
| 3 | ddd-architect | 技术环境、目录规划、横切规范、基础能力清单、改造影响评估 | ARCHITECTURE.md |
| 4 | ddd-decomposer | 目录同构设计文档树，签名级接口契约 | docs/design/**/DESIGN.md |
| 4.5 | ddd-interface-reviewer | 接口契约独立交叉评审，只读 | 接口评审报告 |
| 5 | ddd-implementer | 按就近设计实现代码与单元测试 | 各目录代码与测试 |
| 6 | ddd-test-planner | 制定单元测试计划树 | docs/test/**/TEST_PLAN.md |
| 7 | ddd-fixer | 集成收口与按路由单修 C 级代码或 D 级计划 | 修复清单、已尝试方案与约定遵循自检 |
| 8 | ddd-tester | 执行测试，缺陷定级路由 | 测试报告与缺陷路由单 |
| 9 | ddd-arbiter | 定级争议独立仲裁，只读 | 仲裁裁决单 |
| 10 | ddd-doc-sync | 文档一致性巡检，只读 | 漂移清单 |
| 11 | ddd-auditor | 声明面与死代码审计，只读 | 审计报告与修剪清单 |

槽位号为流程位置与排序标识，跨文档引用一律用代理名。代理名是唯一键。

交接链：需求 → 验收 → 架构 → 分解设计 → 接口冻结 → 实现 ∥ 测试规划 → 集成收口 → 测试执行 → 声明面审计。测试执行与实现永不同段。

根会话保留调度、仲裁、用户裁决与最终验收权，不承担实现类工作。

**派发判定。** 第一问固定为「这个任务是只读的吗」。回答是则派 scout，不再查表。

回答否，按产出物查下表选承接者。

| 产出物 | 承接者 |
|---|---|
| 需求文档 | ddd-requirements |
| 验收标准 | ddd-acceptance |
| 架构文档 | ddd-architect |
| 分解设计与 DESIGN 修订 | ddd-decomposer |
| 接口评审报告 | ddd-interface-reviewer |
| 代码与单元测试 | ddd-implementer |
| 测试计划 | ddd-test-planner |
| 测试报告与缺陷路由单 | ddd-tester |
| 缺陷修复与集成收口 | ddd-fixer |
| 仲裁裁决单 | ddd-arbiter |
| 文档巡检报告 | ddd-doc-sync |
| 审计报告 | ddd-auditor |
| 代码评审 | reviewer |
| 无匹配产出物 | 根会话直接完成 |

表后三条禁令：

1. 只读任务不得派给任何具备写权限的 ddd-* 代理，即使任务看上去很小。
2. 承接者收到不符合自身职责的任务时停止并报告「派发类型不匹配」，注明缺失的前置输入，不得改换任务性质后推进。
3. 该拒绝导致该次子任务验收判 rejected，属预期信号而非代理异常，根会话据此改派或补足前置输入。

承接者合法拒绝任务时，其验收因必需要求项未被满足而判 rejected，这是预期信号而非代理失败：根会话应据拒绝理由改派或补足前置输入，不得要求执行者将就，不得据此认定代理异常。加速档各阶段的任务文本由固定模板给出且输入完整，不触发该情形。

scout 与 reviewer 由 pi-subagents 随带，不在本方法论的十二个代理清单内，派发时使用准确名称 scout 与 reviewer，不加 ddd- 前缀。

## 2. 质量门禁

流程按「序」列推进，未过门退回上一代理并记录于 `<项目根>/docs/gates/`；门号只是标识，序号才是唯一顺序依据。

元规则，顺序固定：

1. 默认规则：本规范中可客观判定的条款均已挂门，门禁表即其归属索引。
2. 例外规则：仅下列条款未挂门，属指导性条款，不得作为验收依据。

未挂门清单：

1. 「问题与解法」节的三条解法陈述：属方法论定位表述，无独立可判定的违反形态。
2. 「并行实现与集成」节的并行前提段：三条前提只描述接缝划分的前置状态，其可判定部分已由 G3 与 G4 的退出条件承接，故该段本身不挂门。
3. 「二次开发」节：是否做现状分析取决于项目是否已有自身规范文档，属设计期判断，无门禁对象。
4. 「本仓库适用边界」节：范围声明，说明本仓库哪些门不适用，不构成对被开发项目的验收要求。

清单外若发现某条本应强制却未挂门的条款，处理方式是补挂门，而非降为建议；判断标准是该条款被违反时能否客观判定，能则必须挂门。

证据源只允许三类：脚本命令，即可复现的机械证据，须写明具体命令；指名代理，即判断型证据，须写明代理名与判据；运行时守卫，即由 pi 扩展在工具调用或收尾时机械判定并阻断，须写明扩展文件与判定编号。

| 序 | 门 | 位置 | 退出条件 | 证据源 |
|---|---|---|---|---|
| 1 | G1 | 需求→验收 | 需求无待确认项；已与用户对齐 | 指名 ddd-requirements 的自查，判据为对齐声明与待确认项为零 |
| 2 | G2 | 验收→架构 | 每条 AC 可客观判定；AC 与需求编号双向可追溯 | 指名 ddd-acceptance 的自查，判据为双向追溯矩阵逐条有对应项 |

| 6 | G5 | 实现→测试执行 | 各接缝自测通过；TEST_PLAN 覆盖全部模块级 AC；高风险用例已桩化或已列入手动测试清单；约定遵循自检已写入完成报告；契约指纹变化时用例集合未逆向缩减 | `node ~/.pi/agent/skills/ddd-methodology/scripts/trace-check.js <项目根>` |
| 7 | G5-INT | 集成收口 | 构建通过；接缝自测报告与约定遵循自检均已写入完成报告；实现文件粒度与设计预判一致；被触碰的超限文件已完成治理或给出拒绝理由；**本阶段未执行全量测试** | `node ~/.pi/agent/skills/ddd-methodology/scripts/code-health.js <项目根>` 与 governance-check 脚本，另加指名 ddd-fixer |

**结构健康度量首版仅报告**，不作为阻断条件；G6 要求的是恶化项逐项给出接受理由或已定级改造，而非恶化项为零。

## 3. 缺陷四级路由

缺陷按四列判定表定级，命中即停；未命中任一级特征时默认取最低适用级别。

| 级别 | 定义 | 自检问题 | 处理 |
|---|---|---|---|
| D 测试级 | 计划漏场景、断言错或覆盖缺口 | 计划是否遗漏或断言错误 | ddd-fixer 修计划 |
| C 实现级 | 实现偏离设计 | 代码与就近 DESIGN 何处不一致 | ddd-fixer 修码，不改设计 |
| B 设计级 | 设计矛盾、边界不清、接口不可实现 | 实现者是做不出来而非没做对 | 重新走分解设计并同步 AC |
| A 需求级 | 设计正确执行仍不满足总 AC | 是否需求本身矛盾或缺口 | 回需求采集，必须经用户确认 |

未命中任一级特征时，默认取最低适用级别。

自检流程按固定顺序：

1. 自问该缺陷是否属 D 级。
2. D 级不成立时自问 C 级。
3. C 级不成立时自问 B 级。
4. B 级不成立时自问 A 级。
5. 命中即停，取该级处理动作。

只有 B 级及以上回设计层。

同一缺陷轮回修复超过 2 轮仍未解决，强制升级用户；仲裁计入轮回。

## 4. 粒度与独立性

粒度阈值集中在本节，是唯一权威定义处：代码文件 500 行、基础或核心模块 300 行、文档 200 行或 10 项契约。其他文档引用阈值时须与本锚点一致，由 `ref-check` 校验。

**文档粒度**：同构场景达到 3 个，或单一 DESIGN 文档超过 200 行或 10 项契约，必须拆解为分类文件或子场景子目录；父级只留共性契约与子场景索引，不重复子场景细节。

**代码粒度**：单文件超过 500 行、基础或核心模块超过 300 行，或承载 2 个及以上独立可测能力，必须拆解；被多模块依赖的基础能力独立成文件并配套独立单元测试；DESIGN 须预判实现文件粒度与职责边界，实现不得合并已拆解文件。

**运行时例外**：受平台约束无法拆解的单文件可视为合规，须同时满足四个判定项：

1. 平台受限：受平台约束无法拆解，如 pi workflow 沙箱脚本因无 `require` 与 `fs` 只能单文件。
2. 文件头显式声明：该约束已在该文件头声明。
3. 单一能力域：文件内容控制在单一能力域内，超出时以任务文本分段而非文件拆分。
4. 未声明不适用：例外须在文件中显式声明，未声明不适用。

**独立性**：模块、类、函数、变量保持相对独立，避免调用顺序影响结果。函数优先无副作用；模块间只经冻结接口通信；类构造完成即可用；变量缩小作用域并优先不可变。契约未标注时序依赖即视为顺序无关，实现不得引入隐式顺序。独立单元测试用乱序调用验证顺序无关性。

## 5. 接口先行与冻结

接口在分解设计期写成签名级契约并冻结为指纹快照，G4.5 五项任一不通过即判 fail。

分解设计期将对外接口写成签名级契约：签名、参数、返回值、错误语义、时序依赖与副作用、消费方模块、调用示例。契约表置于文档前部，调用方只读契约即可集成。

无消费方的接口不得写入契约，也不得引入将来可能用到的预留声明。

冻结的产物是契约指纹快照，不是一个状态词。指纹的构成、变更类型判定与治理义务见「结构与契约的演进治理」节。

G4.5 由 ddd-interface-reviewer 独立评审五项：能力覆盖、模块间重复、模块间缺口、依赖方向、契约质量，另查粒度合规与独立性声明。五项任一不通过即判 fail。结论以 `VERDICT: pass|conditional|fail` 落行；存在能力缺口、重复、依赖违规、粒度违规或无消费方声明时判 fail。

## 6. 并行实现与集成

按依赖约束图划分互斥接缝，一个接缝一个 writer，同一文件任一时刻只有一个写入者。

接缝间只通过 DESIGN 声明的接口耦合，需要改他人接口时停止并报 B 级。

并行前提三条，须逐条成立：

1. 接缝无循环依赖。
2. 设计与测试计划齐备。
3. 横切规范已集中定义。

全部 writer 完成后由根会话收口，再触发集成检查。

## 7. 实现与测试分离

测试规划可与实现并行；测试执行必须在实现收口过 G5-INT 后单独串行启动，与实现永不同段、不共用进程。

G5-INT 与 C 级修复禁止执行全量测试套件；全量测试的唯一主体是 ddd-tester。

## 8. 测试阻塞防护

计划为每条用例标注预估时长与风险级别，并给出含超时的执行命令。

1. 涉及网络、长循环、大数据量、外部服务或真实等待的用例必须桩化，或移入手动测试清单。
2. 执行时只照抄计划中的命令，禁止裸跑。
3. 连续两次超时强制转手动清单。
4. 手动清单由用户执行反馈，待反馈项不阻塞其余缺陷路由。
5. 报告区分自动通过、自动失败、手动待反馈、手动失败四态。

## 9. 需求变更

需求变更走版本化追加与按影响面回归，收口由声明面审计确认。用户变更需求后按下列步骤执行：

1. 登记变更单。
2. 需求与 AC 版本化追加而非覆盖。
3. 依据 AC 双向追溯圈定受影响的 DESIGN 集合。
4. 只对受影响接缝重设计、重实现与回归。
5. 变更完成后派 ddd-auditor 做声明面审计。

## 10. 二次开发

仅当项目缺少自身规范文档时才做现状分析，输出结构推断、原有准则提炼、同构约束清单与风险坑位。已有规范文档时直接对齐，新模块必须与原结构同构。

## 11. 渐进式改造

追加新功能时若现有设计不合理，或结构健康度量相对上次恶化，进入本节的改造分级。

| 级别 | 范围 | 处理 |
|---|---|---|
| L1 文件级 | 单文件内 | 触碰该文件的写入者自行完成并记变更记录，无需根会话派发 |
| L2 目录级 | 单目录多文件 | 分解设计修订 DESIGN |
| L3 模块级 | 跨目录或契约变更 | B 级设计变更走正式路由 |
| L4 架构级 | 目录树或依赖方向 | 根会话确认后修订 ARCHITECTURE |
| L5 项目级 | 技术环境或全局规范 | 必须升级用户确认 |

定级按下列判定顺序：

1. 从 L1 起评。
2. 范围超出该级时上移一级。
3. 命中即停，不得跳级命名。

一次迭代只做一个级别，禁止跨级合并改造。本条约束 L2 及以上。见「结构与契约的演进治理」节的触碰即治理义务，属 L1，不受本条约束。

评估在架构设计期完成，结果写入 ARCHITECTURE 的改造影响评估节，是 G3 的退出条件，其中的存量债务承接列是分解设计者编制粒度预判时的输入；恶化项的定级由根会话依据审计报告在 G6 后派发。

## 12. 声明面可验证与修剪

**铁律：不被消费的声明是危险的，因为无人验证其正确性。**

- [ ] 每条声明同时具备消费方与验证手段，缺一不得引入。

声明面包括接口契约、公开导出、能力清单、规则条款、配置项、模板字段与依赖项。本条的执行入口为 G6，即审计报告未过则不得交付。

审计类代理必须全量核对，不得因看似无用、低风险或成本高而跳过；对每项回答是否被消费与消费是否正确；发现无消费方声明即报缺陷，不得静默留存；反向抽查不少于三项并实测消费路径真的通，专项审计可自行提高下限。

审计必须同时核验**变更记录当轮声称与实际产物是否相符**，声称与实际不符即为缺陷，与代码缺陷同级处理。

无用代码与冗余声明必须删除，不得注释保留，不得以将来可能用到为由滞留。**写入者的清理义务范围限于所触及文件内的连续注释代码与兼容层标记，即文件级属性；无引用文件属仓库级属性，由审计代理处理，不入写入义务。**删除前确认无消费方并登记变更记录。义务的完整性见「结构与契约的演进治理」节的触碰即治理。

写入者的清理义务触发点：结构健康度量显示恶化时、G6 交付前、需求变更后、能力新增后、版本收尾。

审计报告由审计代理在标题下方给出建议归档名，格式为 G6-序号-版本，**序号取 docs/audits/ 现存最大序号加一**；审计代理为只读，**落盘由根会话执行**，写入 `<项目根>/docs/audits/`。**修剪清单在下次审计时必须逐项回验是否真的删除**，回验输入取自该目录内上一份报告。

pi 运行时契约类声明，如 worktree、control 字段与 frontmatter 字段，以冒烟检查与运行时观察为验证手段，不因无法离线验证而判为纸面消费方。

## 13. 结构与注释的机械证据

`node ~/.pi/agent/skills/ddd-methodology/scripts/code-health.js <项目根>` 输出五类事实，作为 G5-INT 的证据源与 G6 审计的输入。度量写入 `<项目根>/docs/health.json`，**该文件入版本管理作为趋势证据，历史上限 50 条**，超出由脚本截断。

| 类别 | 覆盖的事实 | 机械程度 |
|---|---|---|
| 文件规模 | 超 500 行的代码文件、基础或核心模块文件超 300 行、接近上限文件 | 完全 |
| 死代码 | 连续注释代码块、兼容层标记、无引用文件 | 大致，不可达分支需 AST 故未覆盖 |
| 重复嫌疑 | 同名声明跳文件出现 | 弱信号，语义级重复需审计代理判定 |
| 注释 | 违禁模式与提及已不存在标识符的过时引用 | 部分，是否解释为什么不可机械判定，由审计代理抽检 |
| 结构趋势 | 被触碰文件的规模变化，超阈值文件数相对上轮的增减 | 完全 |

默认：上表未列出的结构事实不由 `code-health.js` 输出，须由审计代理语义判定。

度量仅报告不阻断，其阻断地位由 G5-INT 的治理条件承接。度量恶化的具体项写入审计报告的必填节。

脚本消费契约表，消费方按本表解析各脚本的末行结论、退出码与门禁地位：

| 脚本 | 输出形态 | 机读结论 | 退出码 | 门禁地位 | 输出上限 |
|---|---|---|---|---|---|
| trace-check.js | 文本正文 | 末行 `RESULT: pass` 或 `RESULT: gap` | 0 通过，1 存在缺口 | G4 与 G5 门禁 | 12000 字节 |
| code-health.js | 文本正文 | 末行 `RESULT: report` | 恒 0 | 仅报告，不作门禁 | 12000 字节 |
| governance-check.js | 单 JSON | `verdict` 字段 | 0 通过，1 阻断 | G5-INT 门槛 | 12000 字节 |
| ref-check.js | 文本正文 | 末行 `RESULT: pass` 或 `RESULT: drift` | 0 通过，1 存在漂移 | 本仓库文档同步链 | 12000 字节 |

默认：未列入本表的脚本不构成任何门的证据。

各脚本的调用形式统一为 `node ~/.pi/agent/skills/ddd-methodology/scripts/<脚本名>.js <项目根>`；输出上限按 UTF-8 字节计量，超限时截断明细，末行机读结论必须保留且完整。

`node ~/.pi/agent/skills/ddd-methodology/scripts/governance-check.js <项目根>` 输出单项 JSON verdict：每份 DESIGN.md 的契约指纹已记录且与契约段实算值相同，且 `docs/health.json` 最新一条的超阈值文件数不高于上一条时 verdict 为 `ok`，否则为 `blocked`。它作为 G5-INT 的门槛证据，退出码非零即 blocked；命令路径可确定时可经 typed gate 挂载。

## 14. 本仓库适用边界

项目门禁与交付条款面向**被开发的应用项目**；本方法论仓库自身是规范与工具，不含应用代码，其维护只走四条链：

| 适用 | 链路 |
|---|---|
| 文档一致性 | ddd-doc-sync 巡检 |
| 声明面与结构健康 | ddd-auditor 审计，证据源为 code-health |
| 结构治理 | 触碰即治理与存量的粒度、清理、重复治理，证据源为 code-health 与运行时守卫，见「结构与契约的演进治理」节 |
| 改造设计文档 | 位于 `docs/analysis/` 下的版本目录，是本仓库自我迭代的冻结契约来源 |

本仓库的结构性改造按改造设计文档执行，由根会话派发写入代理或由根会话直接实施，改完由文档巡检与声明面审计两条只读链收口。

契约指纹以 DESIGN 为对象，本仓库无 docs/design，故报不适用而非缺口。

不适用：G1、G2、G3、G4、G4.5、G5 的证据源，无论脚本或指名代理。原因是本仓库无 REQUIREMENTS.md、AC.md、ARCHITECTURE.md 与 docs/design，这些门无对象可判；审计中报为不适用而非缺口。trace-check 同样因无 AC.md 在本仓库零可运行范围。

## 15. 状态文件

workflow 加速档以 `<项目根>/docs/.ddd-state.json` 记录进度。

```json
{ "doneStages": ["requirements", "architect"], "lastStage": "architect", "status": "done" }
```

`doneStages` 的阶段键集合与 workflow 的阶段流一一对应：requirements、acceptance、architect、decomposer、interface-review、implement-plan、g5-int、test-execute、audit。`audit` 键由审计阶段写入，用于对齐 workflow 的阶段流。

每个阶段完成后由该阶段代理或其后继写入者合并更新。并行段仅实现者写。JSON 损坏时中断续跑并交根会话，不得当作全新启动。

## 16. 结构与契约的演进治理

### 16.1 契约指纹

DESIGN 的契约表内容取哈希作指纹，版本号由指纹前八位派生。算法唯一权威在本条：

1. 取 DESIGN 中标题为「对外接口与约定」的一节，自该标题起至下一个二级标题前的内容。
2. 剔除其中的契约指纹行本身。
3. 逐行去首尾空白后以换行连接，去尾部空行。
4. 取 SHA-256 十六进制前八位。

指纹是冻结的锚点，回答「冻结的是哪一版」。指纹未变即结构可自由改动，无需审批；指纹变化即行为变更，必须递增版本并走 B 级路由同步 AC，不得静默修改。指纹的机械校验由 trace-check 承担，门槛校验由 governance-check 承担。

### 16.2 变更类型

每次改动须声明类型。重构为契约指纹不变、行为用例全绿、结构度量改善三者同时成立；行为变更为契约指纹变化。声明类型与实际证据不符即为缺陷。

### 16.3 触碰即治理

写入者对所触碰文件的存量结构负治理义务，不限于清理连续注释代码与兼容层标记，代码与文档同等适用，判据为「粒度与独立性」节的粒度阈值。

文件已达或接近阈值时先按就近 DESIGN 的粒度预判拆解，无法拆解方上报。拆解不得超出 DESIGN 预判，超出属设计偏离走 B 级。

写入者完成报告须含结构治理回执，记录被触碰文件的改动前后规模、是否拆解与依据的粒度预判；代码写入者记改动前后行数与是否拆解，文档写入者记产出文档规模与「粒度与独立性」节文档粒度阈值的比对。空节不得声明完成。本义务属 L1，不受「渐进式改造」节一轮一级约束。

### 16.4 等价性验证

测试执行者先判定变更性质。指纹不变时验证用例集合未减少且全绿；指纹变化时核对版本已递增与 AC 已同步，未同步报 B 级。测试用例集合逆向缩减是堆叠信号。

### 16.5 机械约束

可机械判定者分两层承载：声明式门禁为主，运行时守卫为辅。

声明式门禁为代理 frontmatter 的 acceptanceRole、acceptance 与派发 options 的 gate，对所有子代理生效；写入类与审计类代理已显式声明，其余代理沿用 pi-subagents 的默认推断，属分级而非遗漏。写入类代理显式关闭 acceptanceRole 带来的自动评审推断，独立评审由 G4.5 与 G6 承担，避免每次实现重复评审。

运行时守卫由 `extensions/ddd-governance.ts` 在工具调用处拦截，覆盖根会话与后台子代理：

| 编号 | 触发点 | 判定条件 | 动作 | 当前覆盖 |
|---|---|---|---|---|
| H-1 | tool_call 的 write/edit | 估算写入后行数超 500 行 | 拦截，理由含文件路径、就近 DESIGN 路径与拆解要求 | 代码文件 500 行阈值；文件内显式声明运行时例外者放行 |
| H-2 | tool_call 的 bash | 命令属窄口径的全量测试调用形态，且 `docs/.ddd-state.json` 的 lastStage 为 `g5-int` | 拦截，指明全量测试的唯一主体是 ddd-tester | 整仓测试命令的窄口径写法 |

默认：未命中 H-1 与 H-2 的工具调用一律放行。

阈值按档位分配承载：

| 阈值 | 数值 | 承载体 |
|---|---|---|
| 代码文件 | 500 行 | 运行时守卫硬拦（H-1） |
| 基础或核心模块 | 300 行 | `code-health.js` 脚本度量 |
| 文档 | 200 行 | ddd-decomposer 拆解判定与 ddd-auditor 抽检 |
| 文档契约数 | 10 项 | ddd-decomposer 拆解判定与 ddd-auditor 抽检 |

命令级门禁由 `governance-check.js` 承担，命令路径可确定时经 typed gate 挂载，不可用 permission 实现，因其对 bash 恒放行。

守卫豁免：对非 DDD 项目静默，任何异常一律放行并记警告。
