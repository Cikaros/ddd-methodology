# 方法论规范（随 Skill 分发版）

> 与仓库 docs/ 下的规范主文档同源。本文件为 Skill 运行时加载版。

## 1. 核心理念

**分治式设计驱动开发**：文档随架构分治、上下文随职责分治、缺陷随层级路由。

问题根源：大设计文档导致子代理会话记忆负担过高，实现逐渐偏离设计。本质是**上下文与职责不匹配**。

三个基本原则：
1. **上下文最小化**：每个代理只加载与其职责和当前任务直接相关的文档；实现者就近加载，允许按需上溯更高层设计文档防止片面。
2. **文档跟随架构**：设计文档是与目录结构同构的文档树；每个有实现内容的目录一份 `DESIGN.md`，纯结构目录并入父级文档。
3. **缺陷层级路由**：默认最低层判定，自检通过仍失败才上移；争议由根会话仲裁，必要时升级用户。

## 2. 代理职责链

**实现/测试硬分离规则：代理5 规划可与代理4 实现并行（纯产出）；代理6 测试执行必须在实现全部完成、过 G5 收口门后单独串行启动；代理6 与代理4 永不同段、不共用进程。**

```
用户 ⇄ 根会话（调度 + 验证 + 定级仲裁）
   代理1 需求采集 ⇄ 用户确认（未对齐不放行）
   代理0 验收标准（总 AC → 模块 AC 分发）
   代理2 架构师（新建：环境+目录规划 / 二次开发且缺文档：先现状分析）
   代理3 分解设计（目录同构 DESIGN.md 树）
   代理4 实现者 ∥ 代理5 测试规划（均为产出，无进程执行）
   [G5 收口门：实现全部完成]
   代理6 测试执行（单独串行，与代理4 永不同段）→ 缺陷四级路由闭环
```

| 代理 | agent 名 | 职责 | 产出 |
|---|---|---|---|
| 1 | ddd-requirements | 需求细化采集，与用户确认对齐；判定新建/二次开发 | REQUIREMENTS.md |
| 0 | ddd-acceptance | 需求→可执行 AC（G/W/T） | AC.md（总） |
| 2 | ddd-architect | 技术环境、目录规划、横切规范；二次开发现状分析 | ARCHITECTURE.md（+现状分析报告） |
| 3 | ddd-decomposer | 复杂功能分解设计，目录级文档 | docs/design/**/DESIGN.md |
| 4 | ddd-implementer | 就近加载设计文档实现代码与单元测试 | 各目录代码 |
| 5 | ddd-test-planner | 基于总 AC+模块 AC 制定测试计划 | docs/test/**/TEST_PLAN.md |
| 6 | ddd-tester | 执行测试，缺陷定级路由 | 测试报告 + 缺陷路由单 |

## 3. 缺陷四级路由

判定流程、判定规则、路由责任矩阵：唯一权威源为 `references/defect-routing.md`（代理6 执行与根会话仲裁均以它为准；本文不重复定义）。

判定流程、判定规则、路由责任矩阵：唯一权威源为 `references/defect-routing.md`（代理6 执行与根会话仲裁均以它为准；本文不重复定义）。
- 一句话摘要：默认最低层（D/C）判定，自检通过仍失败才上移；仅 B 级及以上回设计层；同一缺陷修复超 2 轮强制升级用户（上限值权威定义见下文§4）。

## 4. 回路终止

**修复轮次上限（权威定义）**：同一缺陷轮回修复超过 **2 轮**仍未解决 → 强制升级用户，禁止继续循环。workflow 加速档的 `maxFixRounds` 默认值以此为准。

## 5. 项目文档体系

```
项目根/
├── REQUIREMENTS.md
├── AC.md
├── ARCHITECTURE.md          # 含横切规范（日志/异常/命名），模块文档只写差异
├── CONVENTIONS.md           # 可选
├── docs/design/<模块>/DESIGN.md   # 与目录同构
└── docs/test/<模块>/TEST_PLAN.md  # 与设计树同构
```

## 6. 二次开发判定

仅当二次开发项目**缺少**自身规范/设计文档时，代理2 才执行现状分析并输出报告；已有规范文档、仅切换会话的情形不符合二次开发定义，直接对齐现有文档。新模块必须与原结构同构。报告格式与检查清单见 process-details.md 主题D。

## 可追溯性校验（G2/G4/G5 门禁依据）

仓库附带只读脚本 `scripts/trace-check.js`（随安装复制到 skill 包 `scripts/`）：解析 AC.md、各 DESIGN.md 验收要点、各 TEST_PLAN.md 用例表，输出未覆盖/悬空引用清单。
- G2 门：总 AC 覆盖全部需求编号无悬空；
- G4 门：模块级 AC 之和覆盖总 AC（trace-check 通过）；
- G5 门：TEST_PLAN 用例覆盖全部模块级 AC（trace-check 通过）；
- 需求变更（主题C 第3步）：以 trace-check 的受影响 AC 编号反查 DESIGN.md，自动产出影响清单。
