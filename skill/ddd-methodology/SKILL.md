# 分治式设计驱动开发

规范唯一权威源为 `references/` 下的规范文件集，以 `references/spec.md` 为索引入口，产物模板见 `references/templates.md`。

## 知识加载规则

知识按三层送达：

1. **代理侧内联**：关键规则已内联在各代理提示词正文，派发即完整送达，不受上下文压缩影响。
2. **流程内联标注**：根会话只在下文各步标注的时机加载对应章节。
3. **规范深读**：完整规则在 `references/` 下的规范各文件，由本 skill 广告与按需读取。

两条显式规则：

1. **送达顺序**：代理侧内联先于流程内联标注，流程内联标注先于规范深读，用于确定加载时机。内联内容是规范的副本，副本与规范冲突时以规范为准，副本漂移由机械校验与文档巡检负责拦截。
2. **主体范围**：「禁止整卷加载 references」只约束子代理，其中「整卷」指整个 `references/` 目录，单份模板或规范文件可按需读取；根会话常驻上下文为 `references/spec.md` 索引与本文件，其余按步骤加载。

## 流程

| 序号 | 阶段 | 代理 | 产出 | 门 | 必读 | 条件读 |
|---|---|---|---|---|---|---|
| 1 | 需求采集 | ddd-requirements | REQUIREMENTS.md，含与用户逐条确认与新建或二次开发判定 | G1 | templates 的 REQUIREMENTS 节 | 项目为二次开发 |
| 2 | 验收标准 | ddd-acceptance | AC.md，需求转为可执行 AC | G2 | templates 的 AC 节 | 无 |
| 3 | 架构设计 | ddd-architect | ARCHITECTURE.md，含技术环境、目录规划、横切规范、基础能力清单、改造影响评估与设计文档树根路径声明；项目级指令文件 AGENTS.md 初版 | G3 | templates 的 ARCHITECTURE 节、templates 的 AGENTS 节 | 项目为二次开发、本阶段产出改造影响评估 |
| 4 | 分解设计 | ddd-decomposer | 目录同构文档树与签名级接口契约 | G4 | templates 的 DESIGN 节 | 产出或修订 DESIGN、涉及接口冻结或指纹变化 |
| 5 | 接口冻结 | ddd-interface-reviewer | 接口评审报告，独立交叉评审 | G4.5 | 规范「接口先行与冻结」节 | 涉及接口冻结或指纹变化 |
| 6 | 实现与测试规划并行 | ddd-implementer 与 ddd-test-planner | 按就近 DESIGN 的实现与单元测试、测试计划树 | G5 | templates 的 TEST_PLAN 节、规范「并行实现与集成」节、规范「测试阻塞防护」节 | 产出或修订 DESIGN |
| 7 | 集成收口 | ddd-fixer | 集成收口结论与结构治理回执 | G5-INT | 规范「实现与测试分离」节 | 本阶段为集成收口或审计、涉及接口冻结或指纹变化 |
| 8 | 测试执行 | ddd-tester | 测试报告与缺陷路由单 | 无 | 规范「缺陷四级路由」节 | 出现定级争议 |
| 9 | 声明面审计 | ddd-auditor | 审计报告与修剪清单，含恶化项 | G6 | 规范「声明面可验证与修剪」节 | 本阶段为集成收口或审计、出现定级争议 |

测试失败的定级与路由见规范「缺陷四级路由」节。争议时派 ddd-arbiter。

过门时按 templates 的门禁检查单填写，写入 `<项目根>/docs/gates/`。检查项取自规范「质量门禁」节的门禁表。

## 条件加载判定

条件加载集中在下表，判据自足，命中即追加对应加载。

| 条件 | 追加加载 |
|---|---|
| 项目为二次开发 | 规范「二次开发」节 |
| 本阶段产出改造影响评估 | 规范「渐进式改造」节 |
| 产出或修订 DESIGN | 规范「粒度与独立性」节与 16.1 契约指纹条 |
| 涉及接口冻结或指纹变化 | 规范「结构与契约的演进治理」节 |
| 本阶段为集成收口或审计 | 规范「结构与注释的机械证据」节 |
| 出现定级争议 | 派 ddd-arbiter，不追加加载 |

默认：未命中上表任何条件时不追加加载。

项目类型由 ddd-requirements 判定，目录内无既有代码与配置为新建，有既有实现为二次开发。ddd-architect 另按项目是否已有规范文档决定是否先做现状分析。两个判据用途不同，不得互相替代。

## 根会话职责

只调度、仲裁与验收，不承担实现类工作。派 ddd-arbiter 处理定级争议，仅最终裁决与升级用户由你决定。同一缺陷超 2 轮强制升级用户。

根会话是被开发项目的调度与验收主体，不受子代理白名单约束，可调用全部已注册扩展工具。机械校验一律由根会话经工具运行，机械证据不接受实现者自陈：`ddd_trace_check` 出 G4 与 G5 的机械证据，`ddd_governance_check` 出契约指纹与趋势门槛，`ddd_code_health` 出结构健康与声明面审计的输入，`ddd_debt_check` 在迭代收尾更新债务登记，`ddd_metrics_report` 在迭代收尾汇总度量。

审计代理为只读，其报告由你按报告给出的建议归档名落盘至 `<项目根>/docs/audits/`，作为下次修剪清单回验的输入。

过门时按 templates 的门禁检查单写入门禁记录至 `<项目根>/docs/gates/`，记录须含 `GATE` 机读行（门号、过门轮次与结论），轮次语义见规范「质量门禁」节。

迭代收尾核验项目级指令文件并做适应性更新，碎片累积到判据时整篇重写。

迭代收尾按规范「绩效度量」节汇总本轮度量并写入 `CHANGELOG.md`。

每轮收尾更新 `docs/debts.json` 的当前版本并录入新增债务，超期项按规范处置。

清偿根因为「机械校验有盲区」的债务时，须把该根因转化为新的机械校验项，并在 `docs/check-coverage.json` 登记根因分类到校验项的映射；登记同根因的新债务时更新既有条目的复发计数与最近复发版本，口径见规范「存量债务的登记与清偿」节。

## 机械门禁

约束不得只靠提示词，派发须绑定机械证据。门禁证据分判断型与机械型两类：机械工具、脚本命令与运行时守卫为机械型，指名代理为判断型；G1、G2、G3 及 G6 的部分子项为判断型，并非全门机械，判据见规范「质量门禁」节。分两层，覆盖面见规范「结构与契约的演进治理」节 16.5。

甲类脚本，即服务被开发项目的机械校验，一律由根会话经对应工具调用而不再拼路径：`ddd_governance_check`、`ddd_trace_check`、`ddd_code_health`、`ddd_debt_check`、`ddd_metrics_report`，每个工具的 `root` 参数传被开发项目根的绝对路径。乙类（服务本仓库自身维护）与丙类（部署与维护辅助）脚本由维护者在本仓库内执行，不进入被开发项目的流程。

- 声明式：写入类与审计类代理的 frontmatter 已声明 acceptanceRole 与 acceptance，派发时按其默认执行；需要额外校验时在 options 传 gate 或 acceptance。
- 运行时：`extensions/ddd-governance.ts` 在 DDD 项目内拦截越阈值写入与全量测试误跑，仅覆盖根会话与后台子代理，前台子代理不加载 ambient 扩展。
- 门槛工具：`ddd_governance_check` 校验契约指纹一致性与超阈值趋势，输出 verdict 作为 G5-INT 证据，见规范「结构与注释的机械证据」节。

脚本的输出形态、机读结论与退出码语义见规范「结构与注释的机械证据」节的脚本消费契约表。

## Workflow 加速档

需求明确且要求一键跑完全链时使用：

```
subagent({ workflow: "<skill目录>/workflows/ddd-workflow.js", args: { root: "<项目根绝对路径>" } })
```

前置条件为加速档用到的 `ddd-*` 代理已安装，未安装将导致派发失败。模型配比属使用者可选增强，由使用者在包目录内自行执行，不属被开发项目流程，模型不得自动触发。完整流程另有手工派发所用的 `ddd-doc-sync` 与 `ddd-arbiter`，不在加速档派发范围内。

加速档覆盖九步，止于声明面审计。审计报告的落盘仍由根会话执行。

| 参数 | 默认值 | 下界 | 说明 |
|---|---|---|---|
| root | 无，必填 | 无 | 项目根绝对路径 |
| maxFixRounds | 2 | 无 | C 与 D 级缺陷自动修复轮数上限 |
| stallTimeoutMs | 300000 | 30000 | 阶段停滞判定超时，单位毫秒 |

脚本按上述流程推进并在 C/D 级缺陷上自动修复重测，A/B 级中断返回本会话。接口评审结论非 pass 时中断并返回本会话，由根会话决定退回分解设计或修复后重跑。状态写入 `docs/.ddd-state.json`，schema 见规范「状态文件」节。

## 派发要求

每次派发须给出目标、cwd、权限边界、相关文档路径、验收标准、期望输出格式与停止条件。实现者任务须列明其负责目录的 DESIGN 路径，禁止要求整卷加载。多模块按互斥接缝并行，一个接缝一个 writer。

派发前先判任务性质。第一问是这个任务是只读的吗。目的只是获取信息、无专属产出物的探查型只读任务，派 scout，不再查表。产出接口评审报告、仲裁裁决单、巡检报告或审计报告等专属产物的职责型只读任务，按产出物查「角色与交接」节的派发表，派对应只读代理。非只读任务同样查表。承接者收到不符合自身职责的任务时停止并报告派发类型不匹配。

只读的探查、调研、方案比选、环境勘察、资料检索，一律派 scout，不得派给任何具备写权限的 ddd-* 代理；该拒绝导致该次子任务验收判 rejected，属预期信号而非代理异常，根会话据此改派 scout 或直接完成。
