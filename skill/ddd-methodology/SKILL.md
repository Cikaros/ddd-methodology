# 分治式设计驱动开发（DDD-Methodology）

完整规范见 `references/spec.md`，文档模板见 `references/templates.md`，缺陷路由详见 `references/defect-routing.md`，多模块并行/需求变更/二次开发细则/质量门禁详见 `references/process-details.md`。**调度任何子代理前必须先通读这些文件。**

## 核心流程

1. **代理1 需求采集（ddd-requirements）**：派发子代理采集细化需求并与用户确认对齐，产出 `REQUIREMENTS.md`（含项目类型判定：新建/二次开发）。未对齐前禁止进入下一步。
2. **代理0 验收标准（ddd-acceptance）**：将需求转为可执行 AC（Given/When/Then），产出项目根 `AC.md`；模块级 AC 由代理3 分发到各 `DESIGN.md`。
3. **代理2 架构师（ddd-architect)**：新建项目→定技术环境与目录规划；二次开发项目且缺少规范文档→先现状分析。产出 `ARCHITECTURE.md`（含横切规范）与目录规划。
4. **代理3 分解设计（ddd-decomposer）**：为每个有实现内容的目录产出同构 `DESIGN.md`，分发模块级 AC。产出 `docs/design/` 文档树。
5. **代理4 实现者（ddd-implementer）与 代理5 测试规划（ddd-test-planner）可并行**：实现者就近加载 DESIGN.md 实现（允许上溯父级/更高层文档）；测试规划者基于总 AC + 模块级 AC 产出同构 `docs/test/` 测试计划树。
6. **代理6 测试执行（ddd-tester）**：按计划执行测试，失败项按四级路由定级处理。

## 根会话职责（你自己的职责）

- 仅调度与验证，不直接实现代码。
- 依据总 `AC.md` 验证交付。
- 缺陷定级争议仲裁；仲裁不了的升级用户。
- 同一缺陷轮回修复超过 2 轮仍未解决 → 强制升级用户，禁止继续循环。

## 缺陷四级路由（摘要，详见 references/defect-routing.md）

| 级别 | 含义 | 处理 |
|---|---|---|
| A 需求级 | 设计无法满足需求/需求矛盾 | 回代理1→用户确认 |
| B 设计级 | 设计缺陷、边界不清、接口矛盾 | 回代理2/3 修订（同步修订 AC） |
| C 实现级 | 设计正确但实现偏离 | 代理4 就地修码，不改设计 |
| D 测试级 | 测试计划本身错误 | 代理5 修计划，代理6 重跑 |

判定规则：默认最低层（C/D）判定，自检通过仍失败才上移一层；仅 B 级及以上才回设计层。

## Workflow 加速档（可选）

当用户明确要求"一键跑完全链"且需求已充分明确时，可使用 workflow 脚本自动推进固定阶段：

```
subagent({ workflow: "<skill目录>/workflows/ddd-workflow.js", args: { root: "<项目根绝对路径>" } })
```

安装后脚本位于 `~/.pi/agent/skills/ddd-methodology/workflows/ddd-workflow.js`；若本机未安装（仅在仓库内开发调试），则使用仓库内 `workflows/ddd-workflow.js` 相对路径。

**前置条件**：7 个 `ddd-*` 代理必须已安装，否则运行时校验失败。脚本通过 `args.root` 接收项目根绝对路径（沙箱中无 process 全局，args 是唯一数据通道）。

脚本会依次执行 需求采集→AC→架构→分解设计→（实现∥测试规划）→测试执行；C/D 级缺陷自动派发修复并重测（最多 2 轮），A/B 级缺陷中断脚本返回本会话仲裁。

**限制**：A/B 级缺陷定级仲裁、超 2 轮未解的缺陷、以及需求变更受理必须回到本会话（根会话）处理，依据 `references/defect-routing.md` 调度。默认仍优先使用手工逐段调度。

## 质量门禁（阶段门）

每阶段交付物必须通过退出条件才可进入下一阶段（G1需求→G2验收→G3架构→G4分解设计→G5实现/测试规划→G6交付，详见 references/process-details.md）。未过门禁一律退回上一代理；并行实现时各接缝需过子门才可集成收口。

## 需求变更（开发中途）

用户变更需求 → 登记变更单 → 代理1/0 版本化修订（追加变更记录，不覆盖历史）→ 代理3 依据 AC 双向追溯圈定受影响 DESIGN.md 集合 → 仅对受影响接缝重设计/重实现/回归。详见 references/process-details.md。

## 实现与测试严格分离（硬规则）

**原则：规划可并行，执行必隔离。**
- 代理5 测试**规划**（纯文档产出）可与代理4 实现**并行**；
- 代理6 测试**执行**必须在实现并行段全部完成、过 G5 收口门之后**单独串行启动**；执行期间禁止任何实现类 writer 运行；
- **代理6 与代理4 永不同段**，严禁二者共用同一 writer 进程/会话；
- 高风险用例（网络IO/长循环/外部等待）必须桩化（stub/mock）或移入手动测试清单，禁止直接自动执行（详见 references/process-details.md 主题F）。

## 测试阻塞防护

实现者与测试者同进程切换运行时，长耗时测试可能卡死进程。防护规则（详见 references/process-details.md 主题F）：
- 代理5 制定计划时对每个用例标注时长/风险级别，并给出**含超时的执行命令**；高风险用例必须桩化或移入手动测试清单，禁止直接自动执行。
- 代理6 **只照抄执行计划中带超时的执行命令**，禁止裸跑；连续 2 次超时强制转手动清单。
- 手动清单由用户手动执行并反馈结果，待反馈项不阻塞其余缺陷路由；测试报告区分 自动通过/自动失败/手动待反馈/手动失败 四类。

## Workflow 状态文件与断点续跑

workflow 加速档每完成一个阶段即写入 `<项目根>/docs/.ddd-state.json`（阶段序号、状态、轮次、缺陷摘要、已过门记录）；再次启动时读取该文件，已完成阶段自动跳过，从断点续跑。中断返回时附带最近一道已过门记录。

## 子代理调度要求

- 每次派发必须在任务描述中给出：目标、仓库/cwd、权限边界（可改哪些文件）、相关文档的**具体路径**（就近加载）、验收标准、期望输出报告格式、停止条件。
- 实现者任务必须列明其负责目录的 `DESIGN.md` 路径，禁止要求整卷加载所有设计文档。
- 多模块实现可并行派发（按互斥接缝划分，一个接缝一个 writer，通过 DESIGN.md 声明的接口耦合；集成由根会话统一收口后触发集成测试。详见 references/process-details.md）。
