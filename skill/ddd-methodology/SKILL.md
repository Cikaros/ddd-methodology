# 分治式设计驱动开发（DDD-Methodology）

完整规范见 `references/spec.md`，文档模板见 `references/templates.md`，缺陷路由详见 `references/defect-routing.md`。**调度任何子代理前必须先通读这三份文件。**

## 核心流程

1. **代理1 需求采集（ddd-requirements）**：派发子代理采集细化需求并与用户确认对齐，产出 `REQUIREMENTS.md`（含项目类型判定：新建/二次开发）。未对齐前禁止进入下一步。
2. **代理0 验收标准（ddd-acceptance）**：将需求转为可执行 AC（Given/When/Then），产出项目根 `AC.md`；模块级 AC 由代理3 分发到各 `DESIGN.md`。
3. **代理2 架构师（ddd-architect)**：新建项目→定技术环境与目录规划；二次开发项目且缺少规范文档→先现状分析。产出 `ARCHITECTURE.md`（含横切规范）与目录规划。
4. **代理3 分解设计（ddd-decomposer）**：为每个有实现内容的目录产出同构 `DESIGN.md`，分发模块级 AC。产出 `docs/design/` 文档树。
5. **代理4 实现者（ddd-implementer）与 代理5 测试规划（ddd-test-planner）可并行**：实现者就近加载 DESIGN.md 实现（允许上溯父级/更高层文档）；测试规划者基于总 AC + 模块级 AC 产出同构 `docs/test/` 测试计划树。
6. **代理6 测试执行（ddd-tester）**：按计划执行测试，失败项按四级路由定级处理。

## 根会话职责（你自己的职责）

- 仅调度与验证，不直接实现代码。
- 依据总 `AC.md` 验证交付。
- 缺陷定级争议仲裁；仲裁不了的升级用户。
- 同一缺陷轮回修复超过 2 轮仍未解决 → 强制升级用户，禁止继续循环。

## 缺陷四级路由（摘要，详见 references/defect-routing.md）

| 级别 | 含义 | 处理 |
|---|---|---|
| A 需求级 | 设计无法满足需求/需求矛盾 | 回代理1→用户确认 |
| B 设计级 | 设计缺陷、边界不清、接口矛盾 | 回代理2/3 修订（同步修订 AC） |
| C 实现级 | 设计正确但实现偏离 | 代理4 就地修码，不改设计 |
| D 测试级 | 测试计划本身错误 | 代理5 修计划，代理6 重跑 |

判定规则：默认最低层（C/D）判定，自检通过仍失败才上移一层；仅 B 级及以上才回设计层。

## Workflow 加速档（可选）

当用户明确要求"一键跑完全链"且需求已充分明确时，可使用 workflow 脚本自动推进固定阶段：

```
subagent({ workflow: "<skill目录>/../../ddd-workflow.js", cwd: "<项目根>" })
```

脚本路径：安装后位于 `~/.pi/agent/skills/ddd-methodology/` 同级的 workflows 目录不可用时，从仓库 `workflows/ddd-workflow.js` 获取；脚本会依次执行 需求采集→AC→架构→分解设计→（实现∥测试规划）→测试执行。

**限制**：脚本只自动推进固定阶段；缺陷四级路由（A/B/C/D）与定级仲裁必须回到本会话（根会话）处理，测试报告返回后按 `references/defect-routing.md` 调度修复轮次。默认仍优先使用手工逐段调度。

## 子代理调度要求

- 每次派发必须在任务描述中给出：目标、仓库/cwd、权限边界（可改哪些文件）、相关文档的**具体路径**（就近加载）、验收标准、期望输出报告格式、停止条件。
- 实现者任务必须列明其负责目录的 `DESIGN.md` 路径，禁止要求整卷加载所有设计文档。
- 多模块实现可并行派发（每个 writer 负责互斥的目录，一个目录只有一个 writer）。
