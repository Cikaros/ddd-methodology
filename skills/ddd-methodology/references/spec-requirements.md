# 需求规范（spec-requirements）

## 四问（缺一不可设计）

1. **谁在什么场景遇到什么**：使用者与触发条件。
2. **要什么可观察的结果**：结果是可见的行为/读数，不是内部实现。
3. **怎么判断做对**：可判定的验收线索（脚本或明确动作）。
4. **本次明确不做**：边界，防实现期无限扩张。

## 澄清记录结构

- 每条需求给**编号**与**可判定线索**两列；线索须能由脚本或明确动作判定。
- 重大决策另出**书面论证稿**（四列对比表：备选项｜证据｜代价｜后续走向），落 `docs/audits/` 并登记 `docs/temp.jsonl`，裁决后清理。

## 冻结判断面

- 四问齐备；**待决项为空**；每条验收线索都可判定。
- 冻结即归并：剔正文内联的变更记录痕迹，重构成「当前即事实」的终稿。

## 证据分级

- 每条论据标来源与强度（直接证据／转述／推断）；**不接受自述完成**。

> 需求类型/状态取值见术语表；G1 的编号与判据见概要设计，本件只引用。
