## 1. 角色与交接

派发前先回答一个问题，答否再查表；角色只由代理名标识，节点键仅作位置与排序标识，跨文档引用一律用代理名。

固定代理十份，随包提供，与节点表一一对应：

| 代理 | 所属节点 | 职责 | 产出 |
|---|---|---|---|
| ddd-requirements | requirements | 细化需求，与用户逐条确认对齐，判定新建或二次开发 | REQUIREMENTS.md |
| ddd-architect | architect | 技术环境、目录规划、横切规范、基础能力清单、改造影响评估 | ARCHITECTURE.md、AGENTS.md 初版、GLOSSARY.md 初版 |
| ddd-acceptance | acceptance | 需求转可执行验收标准 | AC.md |
| ddd-decomposer | decomposer | 目录同构设计文档树，签名级接口契约与实现文件粒度预判 | 目录级 DESIGN.md 树 |
| ddd-detail-designer | detail-design | 文件级设计与实现义务条目 | DESIGN-源文件名.md |
| ddd-interface-reviewer | interface-review | 接口契约独立交叉评审，只读 | 接口评审报告，末行 VERDICT |
| ddd-implementer | implement | 按就近设计实现代码与单元测试 | 所辖目录源码与单元测试 |
| ddd-test-designer | test-plan | 制定单元测试计划 | 同目录 TEST.md |
| ddd-fixer | g5-int、defect-fix | 集成收口，并按缺陷路由单修复 | 修复清单、已尝试方案与结构治理回执 |
| ddd-tester | test-execute | 执行测试，缺陷定级路由 | 测试报告与缺陷路由单 |

项目级代理两份，不随包提供，由模板初始化后归被开发项目所有：

| 代理 | 所属节点 | 职责 | 产出 |
|---|---|---|---|
| ddd-auditor | audit | 声明面审计，只读 | 审计报告与修剪清单 |
| ddd-doc-sync | doc-sync | 文档一致性巡检，只读 | 巡检报告 |

不承接节点的角色：五个交叉检查节点由脚本承担，probe 由外部探查者承担，self-design 与 self-write 由根会话与分域写入代理承担。同一代理在不同节点的注入内容不同，故代理定义内不写节点专属规则。

交接链：需求 → 架构 → 验收 → 分解设计 → 详细设计 → 接口冻结 → 实现 ∥ 测试规划 → 集成收口 → 测试执行 → 声明面审计。测试执行与实现永不同段。

根会话保留调度、仲裁、用户裁决与最终验收权，不承担实现类工作。定级争议的仲裁并入根会话，不再外派独立代理；裁决须引用具体规范条款与被批驳主张，裁决记录写入缺陷路由单的裁决节。

**派发判定。** 派发前先判任务性质。第一问是这个任务是只读的吗。目的只是获取信息、无专属产出物的探查型只读任务，派 scout，不再查表。产出接口评审报告、巡检报告或审计报告等专属产物的职责型只读任务，按产出物查下表，派对应只读代理。非只读任务同样查表。

| 产出物 | 承接者 |
|---|---|
| 需求文档 | ddd-requirements |
| 架构文档 | ddd-architect |
| 验收标准 | ddd-acceptance |
| 分解设计与目录级设计修订 | ddd-decomposer |
| 文件级设计 | ddd-detail-designer |
| 接口评审报告 | ddd-interface-reviewer |
| 代码与单元测试 | ddd-implementer |
| 测试计划 | ddd-test-designer |
| 测试报告与缺陷路由单 | ddd-tester |
| 缺陷修复与集成收口 | ddd-fixer |
| 文档巡检报告 | ddd-doc-sync |
| 审计报告与修剪清单 | ddd-auditor |
| 代码评审 | reviewer |
| 无匹配产出物 | 根会话直接完成 |

表后四条禁令：

1. 只读任务不得派给任何具备写权限的 ddd-* 代理，即使任务看上去很小。探查型只读派 scout，职责型只读派对应只读代理。
2. 承接者收到不符合自身职责的任务时停止并报告「派发类型不匹配」，注明缺失的前置输入，不得改换任务性质后推进。
3. 该拒绝导致该次子任务验收判 rejected，属预期信号而非代理异常，根会话据此改派或补足前置输入。
4. 派发任务的检索一律限定在给定目录内并带路径参数，禁止不带路径的检索与全盘扫描；单条命令超时即放弃并换用更窄的检索面。

承接者合法拒绝任务时，其验收因必需要求项未被满足而判 rejected，这是预期信号而非代理失败：根会话应据拒绝理由改派或补足前置输入，不得要求执行者将就，不得据此认定代理异常。

scout 与 reviewer 由 pi-subagents 随带，不在本方法论的十份固定代理与两份项目级代理清单内，派发时使用准确名称 scout 与 reviewer，不加 ddd- 前缀。

### 1.1 执行模型

本方法论采用固定编排与只读写二分，不采用自主性连续谱分级。编排由本节的角色表与交接链固定；工具集按写入与只读二分，只读代理不持写权限，写入代理不承担审计与巡检；代理的自主范围由职责、工具集与越界升级机制三者界定，三者之外无自主空间，不存在按自主度连续分级的选择空间。

执行模型与「渐进式改造」节的 L1 至 L5 改造分级是两个不同的量：改造分级衡量单次改动的范围，与代理自主度无关；两者名称相近但语义不同，不得混用，也不得以改造级别推定代理自主度。
