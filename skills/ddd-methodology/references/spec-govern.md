本文件承载「本仓库适用边界」「状态文件」「结构与契约的演进治理」三节；不包含面向应用项目的门禁、变更与重建条款。

## 15. 本仓库适用边界

项目门禁与交付条款面向被开发的应用项目；本方法论仓库自身同样按本方法论管理，**不豁免任何门禁**。二者差异只在产物落点与承接方，不在门的适用与否。

| 适用 | 本仓库的做法 |
|---|---|
| 文档一致性 | ddd-doc-sync 巡检 |
| 声明面与结构健康 | ddd-auditor 审计，证据源为 code-health |
| 结构治理 | 触碰即治理与存量的粒度、清理、重复治理，证据源为 code-health 与运行时守卫，见 governance-code 与「结构与契约的演进治理」节 |
| 术语表维护 | 根会话在迭代收尾核验更新，其条目时效性判据同项目级指令文件 |
| 改造设计文档 | 位于本仓库内部档案区（见公开索引 `docs/README.md`），是本仓库自我迭代的冻结契约来源，属内部档案，不随公开仓库发布；历史改造与重建设计记录归档于同一内部档案区 |

本仓库的门禁证据源与其他项目同规。REQUIREMENTS.md、AC.md、ARCHITECTURE.md 与设计文档树按本仓库实际建立情况判定：已建立者按门禁表逐条判，未建立者报不适用而非缺口，但该不适用是「对象尚未建立」的中间态，不是永久豁免。本仓库经项目初始化落项目级骨架后，对应门随之进入适用。

本仓库的结构性改造按改造设计文档执行，由根会话派发写入代理或由根会话直接实施，改完由文档巡检与声明面审计两条只读链收口。

本仓库自身的审计记录归档于内部档案区（见公开索引 `docs/README.md`），属内部档案，不随公开仓库发布；被开发项目的审计归档位置仍为 `<项目根>/docs/audits/`，两侧边界不得混用。

存量重建节面向被开发的应用项目；本仓库自身的重建按改造设计文档执行，产物落内部档案区。

## 16. 状态文件

全链以 `<项目根>/docs/.ddd-state.json` 记录进度。

```json
{
  "channel": "A",
  "doneStages": ["requirements", "architect"],
  "lastStage": "architect",
  "status": "running",
  "freezeAnchor": { "anchor": "<commit sha>", "at": "<时间>" }
}
```

`channel` 与 `freezeAnchor` 为新增字段：前者防止跨通道误续跑，取值 A、B 或 C；后者记冻结锚点，字段结构以设计文档树的冻结清单为准。

`doneStages` 的阶段键集合按通道取 `SKILL.md` 第一节的阶段键表，三通道互不混用。

每个阶段完成后由该阶段代理或其后继写入者合并更新。并行段仅实现者写。JSON 损坏时中断续跑并交根会话，不得当作全新启动。

环境记录 `<项目根>/docs/.ddd-env.json` 与状态文件同落 `docs/` 下，但性质不同：它由初始化 `/ddd-init` 经 `node skills/ddd-methodology/scripts/env-probe.js <项目根绝对路径>` 探测生成，落四类工具的路径、版本与可用性，以及由工具推导出的各语言可用命令形态，供命令组装读取，其结构以下条环境记录键集声明为准。该件随机器而异，同一仓库在不同机器上探测结果不同，纳入版本控制会让不同机器互相覆盖并误导读命令组装者，故不纳入版本控制，由 `.gitignore` 排除；每台机器初始化或维护时重新探测覆盖。

环境记录键集：顶层 `probedAt`、`tools`、`languages`、`frameworks`；逐工具 `path`、`source`、`version`、`available`、`manager`、`versions`、`active`。

## 17. 结构与契约的演进治理

### 17.1 冻结锚点与接口节 diff

契约指纹已废弃，见 DESIGN-decisions.md 的 D20 与 D53；变更判定改由接口节的范围限定 diff 承接。冻结锚点是冻结时刻的 git commit 引用，记于设计文档树的冻结清单 `docs/design/FREEZE.json`，结构为 `{ "anchor": "<commit sha>", "at": "<时间>", "scope": "docs/design" }`。算法唯一权威在本条：

1. 取 DESIGN 中标题为「对外接口与约定」的一节，自该标题起至下一个同级标题前。该标题属目录级契约节，与文件级的「对外接口清单」节不同层，定位时不得混淆，否则非接口段落的改动会被误判为行为变更。
2. 对冻结锚点下的同一文件取同节内容，两侧逐行去首尾空白后比较。
3. 两侧一致即接口未改，区间外的改动不进入判定，不算行为变更。
4. 两侧不一致即接口节 diff 非空，为行为变更。

接口节 diff 为空即结构可自由改动，无需审批，但仍须遵守粒度预判与触碰即治理义务，见 governance-code 技能；无需审批不等于无需设计预判；diff 非空即行为变更，必须递增版本并走 B 级路由同步受影响 AC，不得静默修改。定位与 diff 的实现唯一在 `skills/ddd-methodology/scripts/lib/freeze.js`，机械校验由 trace-check 承担，门槛校验由 governance-check 承担，两脚本共用同一实现：diff 非空且受影响 AC 未同步即判 blocked。被开发项目须为 git 仓库，非 git 项目退化为快照文件比对，本版不实现该退化路径。

### 17.2 变更类型

每次改动须声明类型。重构为接口节 diff 为空、行为用例全绿、结构度量改善三者同时成立；行为变更为接口节 diff 非空。重建为整体替换既有实现与文档，属行为变更的特例，须附废弃清单与回溯点，等价性以 AC 全量回归验证。声明类型与实际证据不符即为缺陷：声明重构却接口节 diff 非空、或声明行为变更却 diff 为空，governance-check 均判 blocked。

### 17.3 触碰即治理

本节判据已移入 governance-code 技能，含治理义务范围、拆解依据与结构治理回执字段；本节只留指针，不重复其定义。

### 17.4 等价性验证

测试执行者先判定变更性质。接口节 diff 为空时验证用例集合未减少且全绿；diff 非空时核对版本已递增与 AC 已同步，未同步报 B 级。测试用例集合逆向缩减是堆叠信号。

### 17.5 机械约束

本节判据已按对象移入治理类技能：阈值承载体、守卫拦截面与豁免归 governance-code 技能，文档类阈值与锁定项归 governance-document 技能。守卫覆盖面、看板注入与命令级门禁归属扩展实现，技能不复制其定义，只给指针。

### 17.6 项目级指令文件的维护

项目级指令文件指置于项目根的 `AGENTS.md`，按模板的五节骨架产出，由运行时逐字注入各子代理的常驻上下文，直接决定子代理看到的项目约定。本仓库自身不落该文件，其维护面向被开发的应用项目。

维护责任与触发，每个触发点均有对应承接方。初版在架构设计期产出，由 ddd-architect 负责：

| 触发点 | 承接方 |
|---|---|
| 能力新增后 | 架构设计期产出或更新 |
| 目录或依赖方向变更后 | 架构设计期产出或更新 |
| 约定变更后 | 架构设计期产出或更新 |
| 结构健康恶化时 | 纳入审计 |
| 迭代收尾 | 根会话核验并做适应性更新 |

不由各写入者各自追加，避免其退化为追加式堆积。

本表的触发点与承接方同时适用于项目根的 `GLOSSARY.md`，其条目时效性核验与内容边界判据同本节上文的维护责任段与内容边界段。

内容边界，写五类，均为项目特有或当前生效者：

1. 项目定位与技术栈。
2. 目录结构与依赖方向。
3. 本项目特有约定与禁忌，逐条带判据。
4. 本项目实际使用的方法论要点，含门禁与产物路径。该类目承载现行机制形态，即机械校验经 `ddd_*` 工具运行并区分 G5 与 G5-INT 的证据产出方，模型与参数按代理 frontmatter 声明，解析器按需经 `/ddd-parser-install` 安装，判定对象不存在时报「不适用」而非缺口。
5. 已知债务与遗留，含接受理由或承接去向。

不写方法论的通用条款。理由是该文件会被复制到每个项目，复制方法论全文会形成副本，与本方法论「单一权威与就近送达」的原则冲突；项目实际使用的部分以要点内联，通用部分保持在方法论本体。

适应性重构的判据：局部过时做适应性修订，不整篇重写；满足下列任一条时整篇重写。

1. 超过文档粒度阈值，阈值与拆分判据见 governance-document 技能。
2. 出现描述与实际不符的条目。
3. 出现无消费方的条目，即项目已不再使用该约定或能力。

这三条与声明面修剪条、文档粒度条和「存量重建」节的判据同源，分别见 governance-declaration 与 governance-document 技能，保持全仓判据一致。

与既有机制的边界，四层不互相替代：

| 机制 | 层级 | 作用 |
|---|---|---|
| 全局规则 | 用户级 | 跨项目强制规则 |
| 方法论规范 | 方法论级 | 跨项目通用条款 |
| 项目级指令文件 | 项目级 | 本项目特有约定与方法论要点 |
| 派发任务文本 | 任务级 | 单次派发的判据内联 |

项目的关键规则若子代理必须看到，写入项目级指令文件或派发任务文本，不得只留在方法论本体。
