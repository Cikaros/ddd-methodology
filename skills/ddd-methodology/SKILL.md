# ddd-methodology（主技能）

## 何时用

当任务涉及**设计驱动的开发**——需求澄清、架构选型、逐层设计、落地实现、测试、收尾、变更记录、冻结与归并——且本仓存在 `docs/ddd/**` 设计树或 `docs/REQUIREMENTS.md` 时载入本技能。只做一次性脚本或纯原型时不必载入。

## 核心流程（大纲）

1. **明确意图**：把需求澄清到四问齐备（谁在什么场景遇到什么／要什么可观察结果／怎么判断做对／本次明确不做）。缺一即不可设计。
2. **架构就位**：定技术栈、核心依赖、目录结构、环境探查四类内容（G2）。
3. **逐层设计**：按四级同构（子项目／模块／分组／文件）落设计件；文件级含四个必备节。
4. **交叉评审**：声明面与实物双向对账四条判据零失败。
5. **测试树**：按设计树逐点落用例文档，编号全局唯一。
6. **落地实现**：按冻结契约写代码与单元测试；**文档先行**，未改设计不得改代码。
7. **执行测试 → 跑门禁 → 记录变更 → 收尾**。

## 三条铁律（不可让渡）

- **文档为唯一权威**：设计变更以文档变更为准，代码为其落地；顺序是「先改文档，再落地代码」。
- **能机械判定的，绝不只写进提示词**：落守卫/权限/门禁（Linter 即 Prompt，带 remedy）。
- **单点权威**：同一事实只在一处写具体值，其余引用；机械取值一律落 `assets/`。

## 冻结即归并（三处各一次）

需求冻结、设计冻结、代码冻结时，各做一次**最终版优化转换**：剔产物**内联**的变更记录痕迹，重构成终稿。归并**按模块/目录隔离**由子代理完成，**不改契约语义**，且**不碰**权威变更流 `docs/CHANGELOG.jsonl`。

## 常见错误

- 在旧文上继续打补丁 → 冻结后仍是「补丁摞补丁」；应重构为终稿。
- 把可机械判定的阈值写进技能正文 → 违反单点权威；应落 `assets/`。
- 混淆「零 FAIL」与「无判定对象」→ 两个读数不得塌成一个。
- 用 `todowrite` 承担持久多步待办 → 会话级、跨会话即丢；持久任务走看板（带 `acceptance`）。
